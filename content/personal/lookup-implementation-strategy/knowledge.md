# Implementation Strategy — 구현 전략

**판단 원칙:** 구현 전에 기존 시스템의 책임과 계약을 확인하고, 선택한 해결책을 현재 코드와 어떻게 연결할지 검토한다. 새로운 구현이나 추상화는 기존 구조로 요구사항을 충족할 수 없는 이유가 확인됐을 때 선택한다.

## 적용 조건

구조 변경, 신규 기능의 구현 방식, 모듈 책임·인터페이스·기술 스택 선택처럼 **구현 선택이 결과나 유지보수 비용에 영향을 미칠 때** 사용한다.

## 판단 기준

- 기존 코드·계약을 재사용하거나 확장해 해결할 수 있는가?
- 변경 책임과 영향 범위는 어디까지인가? 인터페이스를 새로 만들 이유가 있는가?
- 언어·런타임·운영 환경에 적합한 아키텍처나 디자인패턴인가?
- 다른 대안보다 요구 충족도, 결합도, 구현·운영 비용, 검증 가능성이 나은가?
- 중·장기 확장 가능성을 남기되 불필요한 선행 구현은 피할 수 있는가?

**예외:** 작고 명확한 수정에서 기존 계약으로 충분하다면 새 인터페이스·추상화·별도 설계 문서를 만들지 않는다.

## 기존 시스템과 대안의 판단 경계

먼저 현재 요구사항의 관찰 가능한 결과, 관련 코드·테스트, 책임의 소유자, 변경할 계약과 제약을 확인한다. 확인되지 않은 구조를 추정해 '재사용이 가능하다'거나 '새 추상화가 필수다'라고 결정하지 않는다.

| 선택 | 적용 가능한 조건 | 선택하지 말아야 할 경우 |
| --- | --- | --- |
| **재사용** | 기존 모듈의 책임·인터페이스·불변조건을 그대로 충족 | 기존 구현의 숨은 제약 또는 잘못된 책임 경계 때문에 결과가 달라짐 |
| **확장** | 같은 책임에 새 동작이 추가되며 기존 소비자의 계약을 보존·검증 가능 | 조건문·의존성 추가로 서로 다른 책임이 뒤섞임 |
| **분리** | 독립적인 상태·수명주기·규칙·변경 이유가 확인되고 경계를 나누는 이익이 있음 | 단일 사례의 미래 재사용 가능성만 있는 경우 |
| **교체·재설계** | 현 구조로 필수 요구·안전·운영 제약을 만족시킬 수 없고 점진 수정보다 합리적 | 실제 결함 근거 없이 선호 패턴만으로 전면 교체 |

이는 선호 순서가 아니다. 현재 책임이 잘못돼 있으면 기존 코드 재사용보다 분리·교체가 적합할 수 있다.

## 중요한 선택에서 실제로 비교할 기준

1. **기능적 적합성:** 요구 동작·오류·상태 전환·완료 조건을 만족하는가? 만족하지 못하는 후보는 낮은 구현 비용만으로 선택하지 않는다.
2. **계약·호환성:** 외부 API, 저장 데이터, 권한, 사용자 경험, 다른 소비자에 어떤 변화가 있는가? 중요한 변경은 승인이 필요한지 구분한다.
3. **책임과 결합도:** 새 변경이 동일 책임에 속하는가? 작은 수정이 무관한 여러 곳의 동시 변경을 요구하는가? 복잡한 공통 추상화가 오히려 사용자를 결합하는가?
4. **실제 제약:** 언어·런타임·배포·성능·운영·팀의 숙련도에서 해당 선택이 타당한가? 추정 성능 문제를 사실로 취급하지 않는다.
5. **총비용과 검증:** 최초 구현뿐 아니라 마이그레이션·테스트·운영·복구·향후 수정 비용을 비교한다. 확실한 근거가 없는 수치는 추정이라고 표시한다.
6. **되돌리기 가능성:** 실패하면 작게 되돌리거나 점진 전환할 수 있는가? 되돌리기 어려운 계약은 현재 필요한 수준에서 명시한다.

중요한 대안의 경우 *선택한 이유·제외한 주요 대안·남는 위험*을 설명한다. 명백한 작은 수정마다 대안 표, ADR, 별도 추상화를 만들 필요는 없다.

## 설계 결정과 실제 구현의 일치

설계에서 선택한 방식이 실제 구현에도 적합한지는 명칭이나 선언이 아니라 책임·의존성·동작과 요구사항을 근거로 판단한다. 설계와 구현 사이의 불일치가 있으면 그 원인과 실제 영향을 확인한다.

- **책임과 의존성:** 각 구성 요소가 맡은 책임을 수행하고, 변경 이유가 다른 로직의 결합이나 의도하지 않은 의존성이 없는가?
- **패턴의 실효성:** 선택한 패턴이 결합도·변경 용이성·검증 가능성에 실질적으로 기여하는가? 이름뿐인 계층이나 불필요한 추상화는 없는가?
- **구현 관례:** 언어·런타임·운영 환경에서 검증된 구현 방식과 기존 라이브러리를 검토했는가? 직접 구현하는 경우에도 복잡성·제약·장기 유지 비용을 비교했는가?
- **검증의 적합성:** 문서·정적 검사·빌드 결과와 실제 행동·계약을 입증하는 증거를 구분하는가? 선택한 설계의 핵심 불변조건이 실행 결과로 확인됐는가?

어떤 아키텍처·패턴·도구도 보편적 정답으로 강제하지 않는다. 기존 구현을 유지하는 선택과 구조를 바꾸는 선택 모두 요구 충족도, 검증 가능성, 총비용을 근거로 판단한다.

## 중단·재검토

- **설계 종료:** 현재 요구·계약을 만족하는 대안이 확인되고 더 많은 기술 조사로 선택이 바뀔 가능성이 작으면 설계를 확정할 수 있다. 구현 권한을 별도로 확인한다.
- **근거 부족:** 모듈의 책임이나 계약을 확인하지 못하면 조사할 파일·테스트·운영 조건을 먼저 밝힌다. 없는 인터페이스를 지어내지 않는다.
- **재검토:** 새 요구가 기존 책임과 충돌하거나, 실제 결함·변경 빈도·성능·마이그레이션 비용이 추정을 반박할 때 선택을 다시 평가한다.

**다른 원칙과의 경계:** 이 원칙은 *해결책의 구조와 비용*을 선택한다. 작업 위임·병렬화는 Execution Strategy, 미래 기능의 착수 여부는 Roadmap Planning이 판단한다. Node/Step, Gate, Handoff 형식 등 별도 개발 Workflow 절차를 요구하지 않는다.


**근거 수준:** 개발 과정에서 구현 전략과 책임·인터페이스·기술 선택을 반복적으로 검토한 경험에서 *일반화한 후보 원칙*이다. 특정 기술이나 해결책을 모든 상황에 적용하라는 의미가 아니다.
