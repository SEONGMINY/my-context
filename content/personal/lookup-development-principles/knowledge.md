# 개발 판단 원칙

이 문서는 개발 대화에서 **사용자가 반복적으로 요청한 검토 관점**을 토대로 재구성한 실천 원칙이다. 사용자의 발언을 그대로 인용하거나, 각 문장을 사용자가 직접 확정했다고 주장하지 않는다. 확인된 사용자 요구와 여기서 일반화한 판단은 다르다.

적용할 때는 현재 프로젝트의 목표·제약·기존 규칙을 우선한다. 모든 작업에 모든 원칙을 적용하거나 별도 문서를 만들지 않는다. 목적과 복잡성에 맞는 판단 기준만 선택한다.

## 1. Implementation Strategy — 구현 전략

**판단 원칙:** 구현 전에 기존 시스템의 책임과 계약을 확인하고, 선택한 해결책을 현재 코드와 어떻게 연결할지 검토한다. 새로운 구현·추상화는 기존 구조로 목표를 충족할 수 없는 이유가 있을 때 선택한다.

- **적용 상황:** 구조 변경, 신규 기능의 구현 방식 결정, 기술·프레임워크·인터페이스 선택
- **검토:** 기존 코드와 계약으로 해결 가능한가? 변경 책임은 어디에 있는가? 기존 인터페이스를 재사용·확장할 수 있는가? 언어·런타임·운영 환경에 적합한가? 더 단순한 대안의 비용·위험은 어떤가?
- **선택 기준:** 요구 충족도, 영향 범위, 결합도, 구현·유지보수 비용, 검증 가능성. 필요한 경우에만 여러 대안이나 인터페이스를 구체적으로 작성한다.
- **예외:** 작고 명확한 수정에서 기존 계약이 충분하다면 새로운 아키텍처 검토·인터페이스 생성 절차를 요구하지 않는다.
- **대화에서 도출한 맥락:** SDD와 Hide 통합, 코드·인터페이스 연결 검토, Rust 도입 필요성, 기존 MCP로 사용 흐름을 해결한 사례. 사례의 선택을 모든 프로젝트의 정답으로 일반화하지 않는다.

## 2. Execution Strategy — 실행 방식

**판단 원칙:** 작업을 독립적인 단위로 분해하는 것과 이를 실제로 병렬 실행할지는 별도로 결정한다.

- **적용 상황:** 여러 Task, Sub-agent 위임, 병렬 조사·구현, 의존성과 인계가 있는 개발
- **검토:** 후속 작업이 선행 결과를 필요로 하는가? 단일 Agent·순차·병렬·조사만 위임 중 무엇이 적절한가? 위임·컨텍스트 전달·중복 탐색·파일 충돌·통합 검증 비용은 얼마인가?
- **선택 기준:** 실제 완료 시간과 결과 품질에 대한 기대 이익이 추가 비용·위험을 정당화하는가? 중요한 계약 변경과 차단 사항을 필요한 작업자에게 전달할 수 있는가?
- **예외:** 독립 Task가 여러 개여도 규모가 작거나 같은 계약·파일에 강하게 결합됐다면 단일 실행이 나을 수 있다. 병렬 실행의 효과를 실측하지 않았다면 개선됐다고 단정하지 않는다.
- **대화에서 도출한 맥락:** Sub-agent 병렬화를 제안하면서 Task 의존성·맥락 이어짐·실시간 진행 상황 공유의 필요성을 함께 검토하도록 요청한 사례.

## 3. Roadmap Planning — 단계별 계획

**판단 원칙:** 지금 해결해야 할 문제, 실사용 이후 판단할 확장, 장기 방향을 구분한다. 미래를 고려한다는 이유만으로 미래 기능을 지금 구현하지 않는다.

- **단기:** 현재 목표와 완료 조건에 필수적인 변경을 정의한다.
- **중기:** 사용 후 어떤 문제·검증 결과·운영 조건이 나타나면 다음 단계로 진행할지 정한다.
- **장기:** 방향과 제약, 보존할 선택지를 검토한다. 구현하지 않을 부분과 재검토 조건을 명시한다.
- **검토:** 나중에 결정해도 되는 것은 무엇인가? 지금 결정하지 않으면 되돌리기 어려운 계약은 무엇인가? 단계별 의존성과 실제 사용자 가치가 있는가?
- **예외:** 간단한 수정에 단기·중기·장기 로드맵을 의무적으로 작성하지 않는다. 기간과 세부 이정표는 프로젝트별로 정한다.
- **근거 상태:** 대화에서 단계별 구현 범위를 검토한 사실은 확인되지만, 모든 중·장기 질문의 원문과 당시 확정한 세부 기준이 확인된 것은 아니다. 이 항목은 해당 논의에서 **일반화한 후보 원칙**이다.

## 4. Context-aware Reasoning — 상황별 판단

**판단 원칙:** 질문의 목적과 결정의 영향 범위를 파악하고, 그 결정을 실제로 바꿀 수 있는 요소에 집중한다.

| 결정하려는 것 | 우선 검토할 요소 |
| --- | --- |
| 문제와 요구사항 | 기대 결과, 실제 문제, 기존 합의, 영향 큰 불확실성 |
| 구현 방식 | 코드·계약, 책임 경계, 인터페이스, 대안과 기술 제약 |
| 실행 방식 | 작업 의존성, 분해, 위임 비용, 컨텍스트·통합 |
| 중·장기 범위 | 현재 가치, 선행 조건, 재검토 계기, 장래 제약 |
| 기존 결정의 적합성 | 당시 근거, 현재 관찰, 반례, 변경 비용 |
| 완료 여부 | 수용 조건, 실행한 검증과 증거, 남은 미확인 항목 |

- 여러 체크리스트를 무조건 실행하지 않는다. 확인할 사항이 실제 결론을 바꿀 때 조사·질문을 확장한다.
- 확인된 사실·사용자의 결정·AI의 제안·미검증 가정을 구분한다. 모호성을 해소하지 않은 채 이전 결정을 임의로 덮어쓰지 않는다.

## 공통 활용 기준

- **재사용 우선:** 기존 구현·원칙을 확인하되, 기존 방식이 현재 요구를 충족하지 않으면 새로운 접근도 비교한다.
- **비용 대비 효과:** 구현뿐 아니라 조사, 인계, 검증, 유지보수 비용까지 고려한다.
- **근거와 한계:** 실제로 검토한 대안과 사후에 제시한 대안을 구분한다. 검증되지 않은 효과를 사실로 보고하지 않는다.
- **원칙은 조건부:** 현재 Product의 요구사항·정책이 우선하며, 중요한 결정이 아닌 일상적 수정에 새 절차를 강제하지 않는다.

새로운 대화에서 나온 추가 원칙은 바로 이 문서에 덧붙이지 않는다. 먼저 `extract-development-insights`로 재사용 가능성과 중복 여부를 검토하고, 저장 변경은 `manage-dev-knowledge`의 승인 절차를 따른다.
