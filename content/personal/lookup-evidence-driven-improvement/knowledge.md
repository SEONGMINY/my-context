# Evidence-driven Improvement — 증거 기반 개선 판단

**판단 원칙:** 반복적으로 개선할 가치가 있는 제품·시스템·작업 방식에서는 관측 가능한 증거를 바탕으로 문제와 영향을 판단하고, 원인 가설을 검토한 뒤, 변경이 실제 품질·사용자 결과를 개선했는지 확인한다. 개선을 실행하거나 자동화한다는 사실 자체를 성공으로 보지 않는다.

## 적용 조건

실사용 결과나 실행 데이터가 관측 가능하고, 품질·효율·안정성·사용자 부담을 지속적으로 개선할 필요가 있을 때 사용한다. 검색·AI 시스템·운영 프로세스·개발 도구 등 대상 기술에 관계없이 적용할 수 있다.

**예외:** 작고 명확한 수정, 관측 비용이 효과보다 큰 작업, 증거를 수집할 수 없거나 권한이 없는 환경에 별도 계측·평가·자동화 시스템을 강제하지 않는다. 현재 사용자 요청의 산출물과 권한 범위를 벗어나 변경을 실행하지 않는다.

## 관측과 문제 정의

1. **사실과 해석 구분:** 관측된 행동·수치·오류, 평가자의 해석, 원인 가설, 개선 효과의 예측을 각각 구분한다.
2. **관측 범위 확인:** 어떤 작업·환경·사용자에서 어떤 정보가 수집됐는지, 누락된 구간이 있는지 확인한다. **관측되지 않았다는 이유만으로 실패·미사용을 확정하지 않는다.**
3. **품질 우선:** 시간·토큰·비용·호출 횟수의 감소가 사용자 결과나 정확성의 개선을 의미하지는 않는다. 품질, 안전성, 사용자 부담과 함께 비교한다.
4. **문제의 가치:** 관측한 문제가 실제 결과에 어떤 영향을 주는지, 발생 범위·반복성·개선 가능성과 확인 비용을 검토한다. 단순히 수치가 달라졌다는 이유로 수정하지 않는다.

## 원인 가설과 개선 선택

- 재현되는 증상과 그 증상을 만든 **원인 후보**를 분리한다. 하나의 설명에 바로 고정하지 않고 가능한 대안과 반증 근거를 확인한다.
- 원인이 구조·계약·구현·지침·사용 과정 중 어디에 있는지 살펴보고, 가장 적합한 해결 위치와 변경 범위를 비교한다. 모든 문제를 아키텍처 수정이나 프롬프트 변경으로 해결하려 하지 않는다.
- 개선 가설을 세울 때 **어떤 지표 또는 관찰 결과가 어떻게 달라져야 하는지**, 반대로 어떤 회귀를 허용하지 않을지 정한다.
- 관측 증거가 부족하거나 인과 관계가 확인되지 않았다면 추가 관측·격리 실험·보류 중 적절한 선택을 한다. 추론만으로 효과를 입증했다고 주장하지 않는다.

## 개선 전후의 효과 검증

| 판단 기준 | 확인할 사항 |
| --- | --- |
| **기준선** | 개선 전 조건·버전·관측 범위를 확인할 수 있는가 |
| **효과** | 목표한 문제나 사용자 결과가 실제로 개선됐는가 |
| **회귀** | 기존 정상 동작, 안전성, 호환성에 부작용이 없는가 |
| **효율** | 품질을 유지하며 시간·토큰·운영 비용·사용자 개입이 줄었는가 |
| **비교 가능성** | 입력, 환경, 평가 방법의 변화가 결과를 왜곡하지 않았는가 |
| **지속성** | 개선 효과가 재현되거나 실사용에서도 유지되는가 |

실제 평가를 실행하지 못했다면 **개선안을 작성한 것**과 **개선 효과를 검증한 것**을 분리한다. 테스트 통과가 관측 범위를 넘어선 실사용 성공까지 증명하지는 않는다. 검증 후 효과가 불명확하거나 회귀가 확인되면 가설을 재검토하고 필요하면 보류·복구를 선택한다.

## 변경하지 않는 판단과 중단

- 증거가 없거나 개선 가치가 충분하지 않으면 **변경하지 않음**이 올바른 결과일 수 있다.
- 동일한 가설로 반복 수정해도 효과가 없다면 무제한 재시도하지 않고 원인·검증 방법을 재검토한다.
- 추가 측정·실험·자동화의 비용이 기대 효과를 초과한다면 더 가벼운 확인이나 종료를 선택할 수 있다. 단, 필수 안전·권한·품질 계약을 비용 절감만으로 포기하지 않는다.
- 새로운 증거가 기존 가설을 반박하면 판단을 갱신한다. 모든 과거 데이터를 매번 다시 평가하는 것이 목표는 아니다.

## 경계와 반례

- 검색 호출 횟수가 줄었지만 필수 자산을 찾지 못했다면 **효율 개선만으로 성공이라고 판단하지 않는다**.
- MCP 호출 기록만 있을 때 호출하지 않은 작업을 볼 수 없다면 **자산 활용 누락 여부를 확정할 수 없다**.
- 두 번의 실행 시간이 다르더라도 입력·환경·품질 조건이 달라졌다면 **변경의 효과를 단정하지 않는다**.
- 장애 원인을 찾지 못한 상태에서 오류 메시지만 바꾸는 것은 증상 완화일 수 있다. 실제 목표가 사용자 안내 개선이라면 그 변경 자체가 적절할 수도 있다.
- 실제 증거가 충분하고 변경이 작다면 거대한 분석 루프나 자동화 플랫폼 없이도 개선할 수 있다.

**다른 원칙과의 경계:** 이 자산은 *무엇을 개선할지, 효과가 확인됐는지* 판단한다. 해결 구조와 패턴은 Implementation Strategy, 위험 대응은 Risk Management, 지속적 예방 통제는 Preventive Engineering, 병렬·위임 결정은 Execution Strategy가 담당한다. 실제 실행 절차나 승인·권한은 대상 프로젝트의 계약과 사용자 지시를 따른다.

**근거 수준:** Agentic Context Retrieval 개선 하네스를 논의하며 실행 증거·품질 우선·근본 원인·개선 효과·사용자 부담의 관계를 검토한 대화에서 일반화한 **후보 원칙**이다. 해당 하네스의 운영 효과나 자동 개선 성공이 실측으로 입증됐다는 의미는 아니다.
