# 테스트 코드 작성 가이드

테스트는 요구사항을 표현하는 문서다. 이름만 읽어도 어떤 조건에서 어떤 결과가
나와야 하는지 알 수 있어야 한다. 실패하면 어떤 실제 동작에 결함이 생겼는지
알 수 있어야 한다. 구현을 바꿔도 같은 동작이 유지되면 테스트는 계속 통과해야 한다.

## 1. 무엇을 테스트할지 고른다

순수 로직을 우선한다. 깨졌을 때 영향이 큰 분기, 중요한 비즈니스 조건,
회귀 가능성이 높은 로직에 집중한다. UI에서는 클릭, 입력, 토글처럼 사용자가
직접 체감하는 상태 변화를 검증한다.

예를 들어 예약 가능 수량이 충분하면 요청한 수량만큼 예약되는지가 검증할
업무 규칙이다. 내부 계산 순서를 테스트에 복제하면 그 순서를 바꿀 때
테스트도 함께 바뀐다. 입력과 예약 결과를 확인하면 같은 규칙을 다른
방식으로 구현해도 테스트를 유지할 수 있다.

## 2. 준비·실행·검증이 보이게 쓴다

테스트 본문에는 `given / when / then` 흐름을 드러낸다. `given`에는 결과에
영향을 주는 초기 조건을, `when`에는 실행할 동작을, `then`에는 그 동작으로
생긴 결과를 둔다. 읽는 사람이 세 단계를 한눈에 구분할 수 있게 작성한다.

TypeScript 프로젝트에서는 `${파일명}.test.ts`를 기본으로 쓴다. 예를 들어
`calculatePrice.ts`는 `calculatePrice.test.ts`에서 검증한다. 테스트 파일에서
JSX로 컴포넌트의 실제 사용 예시를 렌더링할 때만 `${파일명}.test.tsx`를 쓴다.
Dialog 사용 예시를 렌더링한다면 `Dialog.test.tsx`에 둔다. 대상 프로젝트의
파일명과 도구에 관한 규칙을 우선한다.

## 3. 이름을 요구사항 문장으로 쓴다

- `describe`에는 `~일 때 > ~이어야 한다` 형식으로 검증할 조건과 기대 동작을
  적는다. 예를 들어 `예약 가능 수량이 충분할 때 > 요청한 수량만큼 예약되어야 한다`
  처럼 쓴다.
- `test`나 `it`에는 `~하면 > ~된다` 형식으로 개별 입력이나 행동의 결과를
  적는다. 예를 들어 `같은 값을 다시 선택하면 > 선택이 해제된다`처럼 쓴다.

테스트 이름에는 조건과 결과만 남긴다. 아래 표현을 피한다.

| 표현 | 이유 |
| --- | --- |
| `선택 값을 계산할 때`, `토글 상태 전이를 검증할 때` | 어떤 결과를 기대하는지 알 수 없다. |
| `undefined를 반환해야 한다`, `배열 뒤에 값이 추가되어야 한다` | 이 예시의 이름에는 내부 표현만 있고 어떤 동작을 보장하는지 드러나지 않는다. |
| `가능해야 한다`, `정상적으로 동작해야 한다` | 성공을 판단할 수 있는 구체적인 결과가 없다. |

`이미 선택된 값을 다시 선택하면 > 해당 항목이 제거된다`처럼 이름만으로
검증할 규칙을 읽을 수 있게 쓴다.

## 4. UI는 실제 사용 형태로 검증한다

작은 사용 예시를 만들고 렌더링한다. 사용자가 보는 텍스트로 조작할 대상을
찾고, 조작 전후 화면에서 무엇이 달라졌는지 확인한다. 아래는 React Testing
Library의 조회·렌더링 도구와 `jest-dom`의 단언을 사용하는 예시다.

```tsx
const DialogExample = () => (
  <Dialog.Root>
    <Dialog.Trigger>열기</Dialog.Trigger>
    <Dialog.Content>
      <Dialog.Title>제목</Dialog.Title>
      <Dialog.Close>닫기</Dialog.Close>
    </Dialog.Content>
  </Dialog.Root>
);

test('열기를 클릭하면 > 대화상자 제목이 보인다', () => {
  // given
  render(<DialogExample />);
  expect(screen.queryByRole('dialog')).not.toBeInTheDocument();

  // when
  fireEvent.click(screen.getByText('열기'));

  // then
  const dialog = screen.getByRole('dialog');
  expect(within(dialog).getByText('제목')).toBeVisible();
});
```

검증 대상은 닫혀 있던 Dialog가 클릭 후 열리고 제목이 보이는 동작이다.
내부 Context 값, private 함수, 마크업의 세부 구조는 직접 검사하지 않는다.
접근성, 포커스, 포털 동작은 요구사항에 명시된 경우에 검증한다.

## 5. Mock은 외부 의존성을 끊는 데 쓴다

외부 의존성 때문에 동작을 검증하기 어려울 때 필요한 범위에서만 mock을 쓴다.
Mock 호출 여부나 내부 객체 간 상호작용을 확인하는 테스트, 값을 전달하거나
함수를 감싸는 코드만 검증하는 테스트는 생략한다. 테스트 결과에서 어떤
업무 규칙이나 사용자 동작을 확인했는지 설명할 수 있어야 한다.

## 6. 커버리지와 좋은 테스트의 기준

커버리지 수치를 채우려고 테스트를 추가하지 않는다. 테스트를 추가할 때는
어떤 동작이 깨졌을 때 이 테스트가 실패하는지 먼저 확인한다.

- 이 테스트가 실패하면 실제로 어떤 결함을 의심할 수 있는가?
- 같은 동작을 다른 방식으로 구현해도 테스트가 통과하는가?
- 검증하는 비즈니스 규칙이나 사용자 동작을 한 문장으로 설명할 수 있는가?
- 테스트가 검증하는 기대 결과를 구현의 계산 과정이나 호출 순서와 독립적으로 설명할 수 있는가?

## 7. 독립성과 반복 실행 안정성

테스트는 다른 테스트의 실행 여부·순서·잔여 상태를 전제로 하지 않는다. 결과에 영향을 주는 입력·시간·외부 상태를 해당 테스트가 직접 준비하고, 필요한 자원은 정리한다. 공통 Fixture는 중복을 줄이면서도 독립 실행과 실패 원인 파악을 유지할 수 있을 때 사용한다.

- 이 테스트만 실행하거나 순서를 바꾸어도 같은 중요한 동작을 검증하는가?
- 다른 테스트의 데이터·전역 설정·Mock 상태가 남아 있어야만 통과하지는 않는가?
- 반복 실행 시 결과가 안정적인가? 실제 통합 계약을 Mock으로 지워버리지는 않았는가?

독립성을 위한 복잡한 격리 계층이 테스트의 회귀 방지 가치보다 비용이 크다면, 대상의 실제 계약과 실행 환경에 맞는 최소한의 격리를 선택한다.
