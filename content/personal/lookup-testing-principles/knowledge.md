# Testing Principles — 중요한 동작의 회귀 검증

**판단 원칙:** 테스트는 중요한 요구사항과 외부에서 관찰할 수 있는 계약을 보호하는 실행 가능한 명세다. 테스트의 개수나 커버리지보다 실제 결함을 발견할 가치, 독립적인 재현성과 변경에 대한 안정성을 우선한다.

## 적용 조건

새 동작의 검증, 회귀 테스트 선정, 테스트 구조·Fixture·Mock의 변경, 기존 테스트 제거·정리 시 적용한다. 순수 함수라는 이유만으로 테스트를 추가하지 않으며, 외부 연동이나 비동기·실패 경로도 중요한 동작이면 검증한다.

## 테스트 대상 선정

- 어떤 요구사항·상태 전이·실패 조건·공개 계약이 깨졌을 때 피해가 있는가?
- 실제 회귀 가능성과 검출 가치가 테스트 작성·유지 비용보다 큰가?
- 구현 세부사항을 바꾸더라도 동일한 결과를 보장한다면 테스트가 유지되는가?
- 검증하지 않는다면 어떤 중요한 결함을 놓칠 수 있는가?

단순 전달·자명한 변환·라이브러리의 구현 자체를 검증하는 테스트는 보호할 동작이 별도로 확인되지 않으면 작성하지 않는다.

## 작성과 명명

- 테스트에는 준비(given)·실행(when)·검증(then)의 흐름이 드러나도록 한다. 자명한 흐름까지 형식적인 주석으로 강제하지 않는다.
- `describe`에는 테스트 대상이나 동작 범위를 나타내고, `test` 또는 `it`에는 **조건과 기대 결과**가 이해되도록 이름을 붙인다.
- 내부 함수 호출 순서나 구현 과정을 기대 결과로 사용하지 않는다. 공개 계약이 반환값·예외·호출 동작을 요구하는 경우에는 그 계약을 정확히 검증할 수 있다.
- 파일명·확장자·테스트 도구는 대상 언어·프로젝트의 규칙을 따른다.

## 독립성·반복 가능성

- 다른 테스트가 먼저 실행됐거나 남겨둔 데이터·상태·전역 설정을 전제로 하지 않는다.
- 테스트가 소유하는 입력·상태·시간·외부 효과를 명확히 준비하고 필요한 자원을 정리한다.
- 공유 Fixture는 중복을 줄이면서 독립 실행과 실패 원인 파악을 유지할 수 있을 때 도입한다.
- 반복 실행, 실행 순서 변화, 격리된 실행에서도 중요한 결과가 달라지지 않는지 확인한다.
- 독립성을 얻기 위해 실제로 검증해야 할 통합 동작을 전부 Mock으로 대체하지 않는다.

## 외부 의존성과 사용 행동

- Mock은 시간·네트워크·외부 시스템 등 테스트 제어가 필요한 경계에 필요한 만큼만 사용한다.
- Mock을 사용해도 핵심 판단·결과가 실제 코드에서 수행되는지를 우선 확인한다.
- 사용자가 관찰하는 동작은 가능하면 실제 사용 흐름과 공개 인터페이스로 검증한다.
- 내부 세부 구현의 호출 여부·순서·횟수만 확인하는 테스트는 공개 계약에 해당하지 않으면 피한다.

## 검증 범위와 유지보수

- 테스트가 통과한 범위와 실행하지 않은 환경·경로를 구분한다. 단위·통합·운영 검증은 서로 대체되지 않는다.
- 검증 가치가 사라졌거나 같은 계약을 불필요하게 중복 검증하는 테스트는 제거할 수 있지만, 보호 공백은 확인한다.
- 불안정하거나 거짓 성공을 내는 테스트를 단순히 비활성화하지 않고 원인·계약과 실행 환경을 확인한다.
- 중요한 결함을 실제로 검출하는가, 변경 후에도 동일한 계약을 보호하는가를 주기적으로 점검한다.

**다른 원칙과의 경계:** 이 자산은 무엇을 어떻게 테스트할지 판단한다. Evidence-driven Improvement는 변경의 실제 효과를, Responsibility-driven Design은 구성 요소의 책임을, Development Workflow는 실행·보고 절차를 다룬다. 다른 자산이나 Workflow 호출을 강제하지 않는다.
