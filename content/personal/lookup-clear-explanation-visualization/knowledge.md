# Clear Explanation & Visualization — 명확한 설명과 시각화

**판단 원칙:** 전달할 정보의 핵심과 관계를 파악하고, 독자의 목적과 이해 수준에 맞춰 이해하기 쉬운 형태로 설명한다. 시각화는 이해를 돕는 선택지이며, 단순화 과정에서 사실·제약·예외·불확실성을 왜곡하지 않는다.

## 적용 조건

복잡한 시스템·개념·결정·변경 사항을 설명하거나, 구성 요소의 관계, 순서, 상태, 의존성, 전후 차이를 이해시키는 것이 중요할 때 적용한다. 일반적인 대화·리뷰·계획·문서·보고 등 전달 매체와 무관하게 판단하되, 짧은 답변만으로 충분하면 추가 형식을 만들지 않는다.

## 설명 설계의 판단 기준

1. **전달 목적:** 독자가 무엇을 이해하거나 결정할 수 있어야 하는가? 이미 아는 내용과 지금 필요한 상세 수준은 무엇인가?
2. **핵심 우선:** 중요한 결론·전체 그림을 먼저 제공하고, 그 결론에 영향을 주는 이유와 제약을 연결하는가?
3. **점진적 상세화:** 한 번에 모든 내부 구현을 나열하지 않고 필요에 따라 구성 요소·근거·예외를 펼쳐 설명하는가? 생략이 잘못된 결론을 만들지는 않는가?
4. **구조적 일관성:** 동일한 요소와 관계를 일관된 명칭·방향·범위로 표현하는가? 독자가 표현 방식 자체를 해석하느라 시간을 쓰지 않는가?
5. **표현의 효용:** 도식화·표·레이아웃이 텍스트보다 관계를 더 명확히 보여주는가? 작성·검토·읽기·유지 비용을 정당화하는가?
6. **정확성:** 확인된 사실과 가정·제안을 구분하고, 중요한 조건·오류·경계·순서를 보존하는가? 그럴듯한 그림으로 근거 부족을 감추지 않는가?

## 표현 수단 선택

| 전달할 정보 | 고려할 표현 | 주의점 |
| --- | --- | --- |
| 짧고 직접적인 사실·설명 | 간결한 문장 | 불필요한 도식화로 핵심을 흐리지 않기 |
| 여러 항목의 차이·선택 기준 | 표 또는 나란한 비교 | 비교 기준이 다르면 억지로 같은 열에 놓지 않기 |
| 구성 요소 사이의 관계·의존성 | 구조도·관계도 | 검증되지 않은 연결·소유권을 그리지 않기 |
| 순서·분기·상태 변화 | 흐름도·상태도·순서도 | 중요한 실패 경로·조건·방향 보존 |
| 현재 상태와 변경 후 상태 | AS-IS / TO-BE 비교 | 관찰된 현재와 제안된 미래를 구분 |
| 단계·계층·그룹을 탐색 | 계층형 구성·적절한 UI | 사용 가능한 매체와 접근성 고려 |

표현 수단은 예시이지 필수 형식이나 우선순위가 아니다. 한 장의 그림으로 모든 정보를 표현하려 하지 않고, 독자가 이해해야 할 관계를 기준으로 범위를 선택한다. 복잡한 그림 여러 개보다 간단한 설명 하나가 나을 수도 있다.

## 도식화할 때 확인할 것

- **대상과 관계:** 무엇을 노드·그룹·화살표로 나타내는지 일관되게 설명할 수 있는가? 같은 선이나 위치가 서로 다른 의미로 해석되지 않는가?
- **방향과 시간:** 원인·호출·소유·데이터 이동·실행 순서처럼 성격이 다른 관계를 동일하게 혼동시키지 않는가?
- **정보의 신뢰 수준:** 확인되지 않은 단계나 연결을 임의로 보완하지 않는가? 가설 또는 제안이면 그 상태가 분명한가?
- **가독성과 환경:** 지원하지 않는 렌더링, 과밀한 노드, 긴 레이블, 읽기 어려운 장식이 이해를 방해하지 않는가? 필요하면 텍스트 구조·표 등 대체 표현을 선택할 수 있는가?
- **전후 비교:** 두 상태를 비교할 때 같은 기준과 범위를 사용하고, 무엇이 달라지는지 설명할 수 있는가?

## 예외와 비적용

- 모든 설명에 다이어그램·AS-IS/TO-BE·표를 함께 넣지 않는다. 사용자에게 특정 형식이 필요 없거나 금지됐다면 따르지 않는다.
- 더 쉽게 보이게 하려고 중요한 오류 조건, 권한, 불변조건, 수치의 전제나 검증 한계를 생략하지 않는다. 상세 수준은 줄이더라도 의미가 달라지지 않아야 한다.
- 실제로 확인하지 않은 구조·수치·경로·개선 효과를 시각적으로 확정하지 않는다. 근거가 부족하면 불확실성을 표시하거나 해당 관계를 그리지 않는다.
- 보기 좋은 그림이나 형식 존재 여부를 이해도·정확성의 증거로 취급하지 않는다. 필요한 경우 독자가 올바르게 이해했는지 결과로 확인한다.
- 특정 도구, 모델, 디자인 시스템, 접근 권한, 추가 Skill 호출을 전제하지 않는다. 시각화 제작을 위한 새 파이프라인·Gate를 자동으로 도입하지 않는다.

**다른 원칙과의 경계:** Context-aware Reasoning은 무엇을 확인·판단할지 정한다. Code Clarity는 코드의 이름·입출력·부작용을 명확하게 표현한다. Domain Storytelling은 업무 흐름을 탐색·모델링하는 절차다. 이 원칙은 이미 파악했거나 적절히 확인한 정보를 **어떻게 전달하면 이해하기 쉬운지**를 판단하며, 분석·설계·도메인 탐색 자체를 대신하지 않는다.

**근거 수준:** 복잡한 분석 결과를 이해하기 쉬운 설명과 도식으로 전달하려는 사용자 피드백에서 일반화한 후보 원칙이다. 특정 시각화 방식의 효과가 모든 상황에서 검증됐다는 의미는 아니다.
