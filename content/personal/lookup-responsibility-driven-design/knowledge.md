# Responsibility-driven Design — 책임과 협력 중심 설계

**판단 원칙:** 구성 요소의 경계는 크기나 기술적 종류만으로 정하지 않는다. 어떤 판단과 행위를 소유하고, 어떤 정보가 필요하며, 누구와 어떤 계약으로 협력하고, 무엇 때문에 변경되는지를 근거로 책임을 할당한다.

## 적용 조건

모듈·객체·함수·컴포넌트 사이의 책임 소유권이 모호하거나, 규칙이 여러 곳에 복제되거나, 변경이 무관한 영역으로 전파되거나, 협력 구조가 이해·검증하기 어려울 때 사용한다. 단순한 구현·유지보수 작업에 별도 모델링이나 전면 재설계를 강제하지 않는다.

## 책임과 협력의 판단 기준

1. **행동과 소유권:** 이 요소가 보장해야 할 결과와 불변조건은 무엇인가? 어떤 판단을 직접 수행하고 어떤 결과를 다른 요소에 요청하는가?
2. **필요한 정보:** 자신의 책임 수행에 필요한 정보만 받는가? 다른 요소의 내부 상태·구현·환경을 불필요하게 알고 있는가?
3. **규칙의 단일 소유권:** 같은 업무 판단을 여러 소비자가 각각 재구현하고 있는가? 호출·계산 위치가 달라도 규칙의 정의와 변경 책임은 명확한가?
4. **협력 계약:** 입력·출력·오류·상태 변경 등 서로에게 기대하는 결과를 설명할 수 있는가? 협력이 내부 구현 대신 공개된 행위·계약을 통해 이루어지는가?
5. **응집도와 변경 이유:** 함께 묶인 코드가 같은 이유로 변경되는가? 서로 다른 정책·수명주기·권한·환경 제약을 하나의 소유자에게 부여했는가?
6. **전체 비용:** 책임을 이동하거나 분리하면 결합·변경 영향·테스트 비용이 줄어드는가? 호출 단계·자료 변환·파일 탐색·추상화 비용은 얼마나 증가하는가?

## 책임 배치와 변경 선택

| 선택 | 적합한 조건 | 주의할 조건 |
| --- | --- | --- |
| **유지** | 책임·협력 계약이 명확하고 변경 영향이 제한됨 | 단지 파일이 작다는 이유로 내부 결합을 간과 |
| **재배치** | 판단·데이터 소유자가 잘못되어 무관한 소비자까지 영향받음 | 역할 이동으로 새로운 양방향 의존성 발생 |
| **분리** | 독립된 규칙·변경 이유·권한·수명주기가 실제로 확인됨 | 단일 책임을 여러 전달 계층으로 쪼갬 |
| **통합** | 분리된 요소가 독자적 판단 없이 동일 책임을 공유하고 조정 비용만 증가 | 서로 독립된 계약이나 보호 경계를 소거 |
| **계약 조정** | 협력자가 내부 구현이나 암시적 상태를 알아야 동작함 | 새로운 범용 인터페이스로 결합을 옮길 뿐인 경우 |

### 규칙과 표현·실행의 구분

- 결과의 의미를 결정하는 규칙과 그 결과를 표시·전달·보관하는 방식이 같은 책임인지 확인한다.
- 여러 소비자가 동일한 정책을 따라야 한다면 기준의 소유자를 하나로 두는 편이 적합한지 평가한다.
- 규칙을 **정의하는 위치**와 규칙을 **호출해 계산하는 위치**는 달라도 된다. 사용 위치의 통일을 강제하지 않는다.
- 외부 상태나 환경에 의존하지 않는 규칙은 명시적인 입력으로 표현할 수 있는지 검토한다. 순수 함수가 항상 정답이라는 뜻은 아니다.

## 검토 종료와 예외

책임 소유권과 협력 경계를 설명할 수 있고, 예상되는 변경이 관련 없는 부분으로 과도하게 전파되지 않으며 분리 이익이 비용보다 작다면 현재 구조를 유지한다. 책임을 가진다는 이유로 모든 요소를 상태를 가진 객체나 독립 클래스로 만들지 않는다. 구성 요소가 조립·전달·표시를 담당하는 것도 정당한 책임일 수 있다.

**다른 원칙과의 경계:** Implementation Strategy는 기술·패턴·기존 시스템과 연결하는 **해결 구조**를 선택한다. 이 자산은 선택된 구조 안에서 **책임 소유권과 협력**을 판단한다. Code Clarity는 구현의 이름·입출력·부작용 표현을, Testing Principles는 동작 검증을 다룬다. 어느 원칙도 다른 원칙이나 Workflow의 자동 호출을 요구하지 않는다.

**근거 수준:** 여러 개발 과정에서 책임·자율성·협력 관계를 검토한 경험을 범용화한 후보 원칙이다. 특정 설계 방식의 효과가 모든 환경에서 입증됐다는 뜻은 아니다.
