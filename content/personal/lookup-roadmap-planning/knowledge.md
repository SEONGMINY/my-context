# Roadmap Planning — 단계별 구현 범위

**판단 원칙:** 지금 해결해야 할 문제, 실사용 이후 판단할 확장, 장기 방향을 분리한다. 미래를 고려한다는 이유만으로 미래 기능을 지금 구현하지 않는다.

## 적용 조건

하나의 요구사항을 여러 단계로 구현하거나, 기술 선택이 미래 확장에 영향을 주거나, **현재 범위와 이후 결정의 경계를 정해야 할 때** 적용한다.

## 판단 기준

- **단기:** 현재 사용자 문제와 완료 조건에 반드시 필요한 것은 무엇인가?
- **중기:** 실제 사용 결과·검증·운영 제약 중 무엇이 확인되면 다음 단계를 시작할 것인가?
- **장기:** 어떤 방향과 제약을 보존할 것인가? 지금 결정하지 않아도 되는 것은 무엇인가?
- 지금 미리 결정하지 않으면 되돌리기 어려운 계약과, 필요해질 때 결정해도 되는 구현을 구분하는가?

**예외:** 단순 수정에 3개 시점의 계획을 강제하지 않는다. 일정, 기한, 단계 구분은 대상 프로젝트에서 결정한다.

## 범위를 결정하는 네 가지 상태

| 상태 | 포함 기준 | 현재 해야 하는 일 |
| --- | --- | --- |
| **지금** | 현재의 사용자 문제·필수 계약·완료 조건을 충족하는 데 필요 | 구현 또는 이번 단계의 명시된 산출물로 확인 |
| **조건부 다음** | 실제 사용·측정·검증 또는 선행 정책이 결정의 근거를 제공해야 함 | 무엇이 확인되면 착수할지와 판단 근거를 남김 |
| **장기 방향** | 제품의 중요한 가능성이나 제약을 보존해야 하지만 지금 기술·범위를 결정할 근거가 부족 | 되돌리기 어려운 경계만 검토하고 구체 구현은 보류 |
| **제외** | 현재 문제와 관계없거나 효과 대비 비용이 낮거나 제품 경계 밖 | 확정된 범위에서 제외하고 그 이유를 설명 |

이는 날짜나 분기별 계획을 강제하지 않는다. 사용자가 요청한 단계 또는 프로젝트 기존 로드맵 구조를 우선한다.

## '지금 구현하지 않음'의 판단 순서

1. **필수 여부:** 사용자에게 약속한 결과, 보안·데이터 안전, 호환성, 현재 완료 조건에 필수인가? 필수라면 'MVP니까 제외'할 수 없다.
2. **증거와 불확실성:** 아직 해결할 필요가 관찰되지 않았는가? 실제 증거가 부족한 미래 사용 가능성은 가설로 남긴다.
3. **연기 비용:** 나중에 바꾸기 어려운 데이터·외부 계약·마이그레이션·안전 경계인가? 연기 비용이 크다면 지금 필요한 *최소 계약*을 확정한다. 미래 구현 전체를 당기지는 않는다.
4. **후속 착수 조건:** 기능을 '다음'에 넣으려면 어떤 현상·지표·사용자 피드백·제약이 확인되면 재검토할지 명시한다. 수치 기준은 증거가 있을 때만 정한다.
5. **종료와 제외:** 관찰해도 실익이 없거나 제품 경계를 벗어나면 후속 후보에서 제외할 수 있다. '언젠가'를 자동 약속으로 취급하지 않는다.

## 재검토와 단계 사이의 이동

- **지금 → 조건부 다음:** 현재 필수 계약을 보존하면서, 확장을 정당화할 실사용 근거가 아직 없을 때.
- **조건부 다음 → 지금:** 사전에 정한 신호가 발생했거나 중요한 새 요구가 확인됐을 때. 단순히 시간이 지났다는 이유만으로 착수하지 않는다.
- **장기·제외 → 재검토:** 대상 사용자, 제품 방향, 안전·법적 제약, 운영 규모가 바뀌어 판단 근거가 달라졌을 때.
- **중단:** 지금의 필수 범위와 후속 선택지가 충분히 구분됐다면 모든 미래 기술을 구체적으로 설계하지 않는다. 반대로 연기할 수 없는 필수 계약은 명확히 결정해야 한다.

## 경계·반례

- 초기 사용자가 필요로 하는 데이터 삭제·복구 조건을 '미래 확장'으로 미루는 것은 현재 필수 안전 조건을 놓치는 결정일 수 있다.
- 미래 대규모 트래픽 가정만으로 초기에 별도 메시지 브로커를 도입하는 것은 현재 가치가 확인되지 않은 선행 구현일 수 있다.
- 미래에 여러 플랫폼을 지원할 가능성이 있어도 지금 표준 데이터 포맷을 정하지 않으면 이전이 매우 어려운 경우에는 최소 호환 계약을 선확정할 수 있다.
- 장기 방향에 적혀 있다는 이유만으로 팀에 확정된 일정이나 구현 의무가 생기지 않는다.

**다른 원칙과의 경계:** 이 원칙은 *범위와 착수 조건*을 판단한다. 구체 구조는 Implementation Strategy, 병렬 실행과 위임은 Execution Strategy, 무엇을 더 확인할지는 Context-aware Reasoning이 담당한다. 별도 계획 파일이나 작업 관리 절차를 새로 요구하지 않는다.


**근거 수준:** 이전 대화에서 단계적 구현 범위와 향후 확장을 구분한 사실에서 *일반화한 후보 원칙*이다. 단기·중기·장기에 대해 실제로 확정했던 모든 문구와 기간은 확인되지 않았다.
