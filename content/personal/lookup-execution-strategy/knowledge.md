# Execution Strategy — 실행 방식 선택

**판단 원칙:** 작업의 특성, 의존 관계, 맥락 결합도, 작업자의 역량, 실제 실행 환경과 비용·효과를 고려해 적합한 실행 방식을 선택한다. 작업을 분해할 수 있다는 사실과 병렬 실행이 유리하다는 사실은 별개다.

## 적용 조건과 경계

독립적인 작업 후보가 여러 개 있거나, 조사·구현·검토를 분리하거나, Sub-agent 위임·세션 전환의 적합성을 판단할 때 사용한다. 작은 변경이나 명확한 단일 작업에 별도 계획 또는 위임을 강제하지 않는다. 현재 프로젝트 계약과 사용자 지시, 실제 도구·권한을 우선한다.

이 원칙은 실행 방식의 선택에 관한 독립적인 판단 기준이다. 작업 상태 관리, Node/Step 형식, 인계 데이터 구조, 결과 수용·승인 및 변경 전파 절차를 정의하지 않는다. 다른 Skill을 호출해야만 적용할 수 있는 원칙이 아니다.

## 실행 대안 비교

| 방식 | 적합한 조건 | 불리한 조건 |
| --- | --- | --- |
| 단일 담당 | 작은 작업, 높은 맥락 결합도, 공유 파일·빠른 결정 | 독립된 장시간 작업으로 대기 시간이 커짐 |
| 순차 실행 | 후속 작업이 선행 결과나 판단을 실제로 필요로 함 | 독립된 작업까지 불필요하게 대기 |
| 병렬 조사 | 탐색 관점·자료가 독립적이지만 공통 결론은 함께 판단해야 함 | 같은 원본을 중복 조사하고 차별화된 결과가 없음 |
| 병렬 구현 | 책임과 계약이 안정적이며 결과를 독립 검증·통합할 수 있음 | 미확정 계약, 공유 자원, 잦은 상호 조정 |
| 부분 위임 | 독립 조사·테스트·검토가 핵심 판단의 집중을 돕고 결과 확인 가능 | 전달·재검증 비용이 예상 이익보다 큼 |

## 작업 분해와 의존성

분리할 작업의 목적과 산출물, 독립 검증 가능성, 통합 이후의 동작을 확인한다. 기능이나 파일이 다르다는 사실만으로 독립성을 가정하지 않는다.

| 의존성 | 판단할 내용 |
| --- | --- |
| 산출물 | 선행 작업의 실제 결과가 필요한가, 안정된 계약만 있으면 되는가 |
| 계약 | 동일한 인터페이스·정책·불변조건에 의존하는가 |
| 맥락 | 기존 결정의 이유·제외 범위·사용자 정정을 알아야 올바르게 판단하는가 |
| 정보 | 실행 중 발견되는 정보가 다른 작업의 선택을 바꾸는가 |
| 자원 | 파일·데이터·환경·권한을 공유해 충돌하거나 대기하는가 |
| 검증 | 결과를 독립 확인할 수 있는가, 통합한 후에만 검증 가능한가 |

함께 바뀌는 책임과 판단은 묶는 것이 유리할 수 있다. 분리할 단위는 각 결과의 가치와 응집도, 분리·조정·통합 비용에 따라 정한다. 단순한 실행 순서 선호를 실제 의존성처럼 취급하지 않는다. 취소된 선행 작업이 있었다면 필요한 입력이 다른 방법으로 충족됐는지 확인한다.

## 담당자와 맥락의 적합성

- **역량과 권한:** 필요한 조사·구현·검증 역량, 도구, 접근 권한을 실제로 갖춘 작업자에게 맡길 수 있는가? 독립 실행이나 격리가 가능한지 확인한다. 제공되지 않는 Sub-agent 기능을 있다고 가정하지 않는다.
- **맥락의 충분성:** 필요한 목표, 계약, 결정 이유, 예외, 관련 선행 결과를 충분하고 정확하게 제공할 수 있는가? 원본을 확인할 수 있는지, 현재 유효한 정보인지, 착수 전에 필요한지 판단한다. 토큰 절감을 위해 판단에 필수적인 이유나 조건을 생략하지 않는다.
- **독립적 판단:** 구현에는 확정 계약과 중요한 이유가 필요하지만 독립 조사·리뷰에는 기존 결론을 그대로 따르도록 유도하지 않는 것이 유리할 수 있다. 공통 요구사항과 실제 증거는 숨기지 않으면서 결론에 대한 불필요한 편향을 줄인다.
- **결과 확인:** 작업자의 설명만으로 충분한가, 실제 결과를 검증할 수 있는가? 검증이 어렵거나 중요한 맥락을 전달할 수 없다면 위임의 이익을 다시 판단한다.

이 기준은 작업자 배정·전달 방식의 적합성에 대한 판단이며 특정 역할 체계나 인계 포맷을 요구하지 않는다.

## 진행 중 정보 공유가 필요한지 판단

먼저 **어떤 중간 정보가 누구의 판단을 어느 시점에 바꾸는지** 확인한다.

| 조건 | 비교할 실행 방식 |
| --- | --- |
| 중간 발견이 다른 작업에 영향 없음 | 완료 후 결과 활용만으로 충분 |
| 일부 발견만 후속 판단에 필요 | 필요한 정보만 적시에 확인 가능한 방식 |
| 중요한 계약·제약의 중간 변경이 즉시 영향을 줌 | 선택적 공유가 가능한 실행 방식 또는 계약의 선확정 |
| 상호 의존이 빈번하고 공유 지연의 피해가 큼 | 작업 경계 재분리, 단일 담당, 순차 실행 |

실시간 공유가 필요하다는 결론과 환경이 이를 지원한다는 사실은 별개다. 실제 접근 권한, 업데이트 인지 가능성, 정보의 최신성과 확인 상태, 전달 지연 및 비용을 확인한다. 공유 지원이 없거나 불확실하다면 중앙 조정, 안정된 공통 원본 참조, 순차 처리 또는 독립 조사 등을 비교한다. 실시간 공유 자체를 목표로 하거나 메시징 시스템 구축을 당연한 전제로 삼지 않는다.

## 이득·비용과 재판단

경과 시간과 총비용을 분리해 비교한다. 병렬화가 경과 시간을 줄이더라도 총 토큰·도구 호출·중복 탐색·맥락 전달·통합·재검증 비용을 늘릴 수 있다. 실제 측정이 없다면 효과를 추정과 구분한다. 중요한 사용자 결과·계약·안전성을 비용 절감의 대가로 희생하지 않는다.

선택에 충분한 근거가 확보됐다면 추가 계획이나 비교를 멈춘다. 실제 실행 불가, 중요한 계약 변경, 공유 지연, 맥락 오해, 반복 재작업, 자원 충돌, 예상 이익 감소가 확인되면 영향받는 작업의 분리와 실행 방식을 다시 판단한다. 기존 독립 결과까지 무조건 폐기하지 않는다. 복잡한 작업에서는 선택한 방식과 제외한 주요 대안의 이유를 설명한다.

## 경계·반례

- UI와 API 파일이 달라도 계약이 미확정이면 병렬 구현보다 독립 조사 또는 순차 결정이 적합할 수 있다.
- 짧은 수정들이 동일 책임·설정·테스트를 공유하면 세분화와 위임이 오히려 손해일 수 있다.
- 중간 발견이 다른 작업의 인증 판단을 바꾸는 경우 완료 후 공유는 늦을 수 있다. 해당 정보를 적시에 참조할 수 없는 환경이라면 실행 방식을 바꾼다.
- 독립 조사 두 건에 실시간 진행 로그를 공유할 필요가 없다면 동기화 비용을 늘리지 않는다.
- 독립 검토자에게 요구사항과 검증할 실제 결과는 제공하되 구현자의 결론을 그대로 재현하도록 요구하지 않는다.
- Sub-agent를 제공하지 않는 환경에서는 가능한 실행 대안을 선택하고 실제 위임 여부와 예상 효과를 구분한다.

**다른 원칙과의 경계:** 구현 구조의 선택, 구현 범위와 시점, 위험 대응, 검증 품질은 각각 다른 판단 목적이다. 실행 방식이 해당 판단에 의존할 수 있지만 이 원칙이 다른 자산이나 개발 Workflow 실행을 강제하지 않는다.

**근거 수준:** 사용자가 작업 분해, 의존 관계, 맥락 이어짐, 필요한 컨텍스트 전달, 실시간 정보 참조의 필요성과 구조적 가능성을 함께 검토하자고 제안한 발언에서 일반화한 후보 원칙이다. 항상 병렬화하거나 모든 정보를 공유하라는 의미가 아니다. 역량·독립 검토·비용 등의 상세 판단은 위 의도를 보완하기 위한 후보이며 과거 확정 선언으로 취급하지 않는다.
