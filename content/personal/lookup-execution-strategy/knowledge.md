# Execution Strategy — 실행 방식 선택

**판단 원칙:** 작업을 독립적으로 분해할 수 있다는 것과 실제로 병렬 실행하는 것이 유리하다는 것은 별개다.

## 적용 조건

독립 Task가 여러 개 있거나 Sub-agent 위임, 조사·구현의 분리, 세션 간 인계처럼 **실행 방식에 선택지가 있을 때** 적용한다.

## 판단 기준

- 각 Task의 실제 산출물과 수용 조건은 무엇인가? 다른 Task의 *수용된 결과*가 필요한가?
- 단일 Agent, 순차 실행, 전체 병렬, 조사만 병렬 위임 중 무엇이 적합한가?
- 예상 절약 시간보다 컨텍스트 전달, 중복 탐색, 파일 충돌, 통합·재검증 비용이 큰가?
- 공유 상태의 소유자는 누구이며, 차단 사항과 중요한 계약 변경을 누구에게 전달해야 하는가?

**예외:** 독립 Task가 많아도 작거나 같은 파일·계약에 강하게 결합돼 있으면 단일 실행이 나을 수 있다. 병렬 실행의 효율을 실제 측정하지 않았다면 개선을 확정하지 않는다.

## 실행 방식 선택의 실제 기준

**먼저 작업의 결과와 선행 조건을 파악**한다. 독립적으로 설명 가능한 Task가 있다는 사실만으로 병렬 실행을 확정하지 않는다. 실행 도구와 권한, 공유 파일·상태·외부 계약을 확인한 뒤 다음 대안을 비교한다.

| 방식 | 유리한 조건 | 피할 상황 |
| --- | --- | --- |
| **단일 Agent** | 작업이 작거나 공통 맥락·동일 파일·빠른 의사결정이 중심 | 서로 독립된 오래 걸리는 조사·구현이 많음 |
| **순차 실행** | 앞선 결과가 후속 작업의 실질적 선행 입력이고 수용 전 후속 실행이 위험 | 근거 없이 모든 독립 작업을 직렬화 |
| **병렬 조사** | 관점·자료는 독립적이지만 결론·계약은 함께 정해야 함 | 동일 원본의 중복 탐색만 늘어남 |
| **병렬 구현** | 경계·입력·계약·파일 소유권이 안정돼 있고 산출물을 독립 검증·통합 가능 | 계약 미확정, 동일 파일 동시 수정, 공유 상태 충돌 |
| **부분 위임** | 검색·테스트·독립 검토만 분리해 주요 판단 맥락을 보호 | 위임 준비와 재검증 비용이 예상 이익보다 큼 |

## 비교 순서

1. **의존성:** 무엇이 다른 작업의 *검증되거나 수용된 결과*를 필요로 하는가? 단순한 실행 순서 선호를 의존성으로 보지 않는다.
2. **계약 안정성·충돌:** 서로 다른 작업자가 동일 책임·파일·데이터를 동시에 변경하는가? 독립 Worktree라 해도 공통 API 변경 충돌은 사라지지 않는다.
3. **이득과 비용 분리:** 병렬화로 줄일 **경과 시간**과 늘 수 있는 **총 토큰·도구 호출·중복 조사·인계·통합·재검증 비용**을 따로 비교한다. 근거 없는 절감률이나 개선을 단정하지 않는다.
4. **실행 가능성:** 지금 환경에 Sub-agent·격리 작업 공간·통합 검증 능력이 실제 있는가? 사용할 수 없는 도구로 위임했다고 주장하지 않는다.
5. **주요 맥락 유지:** 독립 결과만 전달받으면 되는 작업인가, 중요한 원본 맥락을 계속 공유해야 하는가? 후자는 단일 담당 또는 순차 처리가 적합할 수 있다.
6. **선택과 설명:** 위험과 비용을 고려해 방식을 선택한다. 복잡한 작업에서는 선택한 방식과 포기한 대안을 짧게 설명한다.

## 진행 중 전략 전환

- **차단·계약 충돌:** 중요한 공통 계약·보안·권한 문제를 발견한 작업자는 영향을 받는 수정을 멈추고 판단 담당자에게 확인을 요청한다. 이미 유효한 독립 작업까지 무조건 중단하지 않는다.
- **중복·충돌 증가:** 공유 파일 충돌, 같은 조사 반복, 높은 통합 재작업 비용이 확인되면 병렬 구현을 순차 처리 또는 병렬 조사로 전환한다.
- **의존 조건 변동:** 선행 결과가 취소·변경되면 후속 작업의 전제조건을 재검토한다. '취소됨'을 '충족됨'으로 해석하지 않는다.
- **완료 보고:** 파일 변경이나 작업자 자신의 완료 주장은 외부 계약을 만족했다는 증거가 아니다. 허용된 범위의 실제 산출물·검증 결과를 확인하고, 미실행은 미확인으로 보고한다.
- **효율 검증:** 같은 조건으로 비교·측정할 수 없다면 병렬화가 시간이나 토큰을 줄였다고 확정하지 않는다.

## 경계·반례

- 계약 확정 전 UI와 API를 나눠 동시에 구현하면 결과를 합칠 때 계약 재작업이 생길 수 있다. 독립적인 **조사만** 먼저 병렬화하는 대안이 있다.
- 각 문서가 서로 다른 영역이고 검증 가능하다면 병렬 작성이 유효할 수 있지만, 함께 고쳐야 하는 공통 설명은 한 담당자가 통합한다.
- Sub-agent가 없는 환경에서는 단일 실행을 선택하거나 불가능한 위임 사실을 명확하게 보고한다. 가상의 병렬 작업을 완료로 보고하지 않는다.
- 작업을 아주 잘게 분리하면 위임 비용이 산출물의 가치보다 커질 수 있다. Task 수가 많다는 이유만으로 효율을 가정하지 않는다.

**다른 원칙과의 경계:** Implementation Strategy가 *무엇을 어떻게 구현할지*, Roadmap Planning이 *언제 무엇을 구현할지*를 판단한 다음에도 실제 작업 실행 방식은 별도로 선택한다. 이 문서는 에이전트 실행 시스템, 상태 저장 포맷, Handoff 절차를 구현하거나 강제하지 않는다.


**근거 수준:** 사용자가 Task 의존 관계와 맥락 이어짐을 고려한 병렬 Sub-agent 실행을 *제안*하고, 작업 현황의 실시간 공유 필요성까지 *질문*한 과정에서 추출한 후보 원칙이다. 병렬화를 항상 요구한 것은 아니다.
