# Preventive Engineering — 구조적 예방과 재발 방지

**판단 원칙:** 중요한 위험과 반복될 수 있는 실패를 일회성 대응으로 해결할지, 장기적인 구조적 통제로 예방하거나 조기에 탐지할지 판단한다. Gate는 목적이 아니라 가능한 수단 중 하나다.

## 적용 조건과 경계

반복되는 결함·계약 위반, 중요한 데이터·권한 경계, 위험 대응 검토, 단 한 번이라도 피해가 큰 실패 가능성에서 적용한다. 이미 발생한 사고뿐 아니라 실행 전에 확인한 중요한 위험도 대상이다. 일회성 저위험 문제나 근거 없는 미래 위험에 통제를 자동 추가하지 않는다.

통제 검토는 실제 추가·삭제·우회에 대한 권한이 아니다. 프로젝트의 기존 안전·권한·검증 정책을 우선한다.

## 실패 유형과 통제 필요성

개별 사례, 원인, 공통 실패 유형을 구분한다. 특정 문서 링크 하나의 오류를 막는 것과 문서 참조 무결성을 보호하는 것은 다르다. 여러 사례의 공통 원인과 불변조건이 확인된다면 동일 유형을 예방하는 통제를 검토한다. 한 사례만으로 모든 변경을 차단하는 규칙을 만들지 않고 반례와 적용 범위를 확인한다.

| 판단 요소 | 확인할 사항 |
| --- | --- |
| 반복성·근본 원인 | 현재 구조가 같은 실패를 계속 허용하는가 |
| 피해·복구 | 낮은 빈도라도 심각하거나 복구 불가능한 피해인가 |
| 예방 가능성 | 원인 제거 또는 잘못된 상태 자체의 제한이 가능한가 |
| 검증 가능성 | 보호할 계약과 위반 여부를 신뢰성 있게 확인할 수 있는가 |
| 시점·범위 | 피해 전 어느 경계에서 최소 범위로 통제할 수 있는가 |
| 비용·부작용 | 실행·유지비, 지연, 오탐, 추가 권한, 사용자 개입 |
| 책임·수명 | 변경·예외·실패 대응을 관리할 수 있는가 |

단일 사고의 영향이 크다면 반복 경험이 없어도 예방을 고려한다. 위험이 높다는 이유만으로 새 Gate를 확정하지 않고 기존 통제로 충분한지도 확인한다.

## 통제 계층과 수단 선택

| 계층 | 수단 및 선택 조건 | 한계 |
| --- | --- | --- |
| 구조·설계 | 원인 제거, 단순화, 타입·데이터 모델·책임 분리로 잘못된 상태의 생성 제한 | 과도한 추상화·경직성, 외부 입력은 별도 고려 |
| 구현·계약 | 안전한 기본값, 입력·런타임 검증, 권한·데이터 경계 | 중요한 사용자 선택을 임의 기본값으로 대체하지 않음 |
| 테스트·CI | 재현 가능한 계약 위반을 테스트·정적 분석·차단 검사로 확인 | 구현 세부사항이나 문구 검사만으로 실제 동작을 보장하지 않음 |
| 운영 | 관측·경고·피해 격리·복구 | 대응 주체와 시간, 검증된 복구 수단 필요 |
| 판단·권한 | 사람의 검토, 의미적 행동 평가, 승인·권한 제한 | 불필요한 반복 승인과 오탐으로 인한 병목 |

원인이 존재하는 계층과 피해가 발생하는 경계를 먼저 파악한다. 같은 보장에 드는 총비용과 검증 가능성을 비교하며, 반드시 가장 앞선 계층을 선택하거나 모든 계층에 통제를 추가하지 않는다. 구조적 제약으로 충분한 경우 중복 Gate는 필요하지 않을 수 있고, 단일 통제로 남는 위험이 큰 경우 보완 통제를 조합할 수 있다.

## Gate가 적절한 경우

보호할 불변조건과 기존 통제가 충분하지 않은 이유부터 파악한다.

- **판정 가능성:** 실제 위반을 신뢰할 증거로 확인할 수 있는가? 모델의 의미적 판단을 특정 문자열 존재나 파일 유무만으로 증명하지 않는다.
- **시점·강제 수준:** 피해를 막는 데 필요한 시점인가? 위반의 심각성과 판정 신뢰성, 대응 가능성에 따라 차단·경고·리뷰를 비교한다.
- **실패·예외:** 실패 원인과 수정 방법을 알 수 있는가? 정상 작업을 잘못 차단할 가능성은 어떤가? 예외·대체 통제는 기존 권한과 보호 조건을 충족해야 한다. 검사 미실행을 통과로 간주하지 않는다.
- **효과 검증:** 위반 사례를 막고 정상·경계 사례를 허용하는지 확인할 수 있는가? 통제의 검사 범위를 넘어 실제 안전이 모두 보장된다고 주장하지 않는다.

기존 타입·테스트·CI·리뷰·권한 제어를 활용할 수 있는지 먼저 판단한다. 새 실행 시스템이나 일괄적인 Gate 관리 절차를 요구하지 않는다.

## 유지·변경·제거와 종료

반복 실패, 오탐, 비용 증가, 구조 변경, 새로운 위험은 통제 재검토의 근거다. 기존 통제가 충분히 보호하는지, 범위나 위치를 바꿀 필요가 있는지, 더 낮은 비용으로 같은 보장이 가능한지 비교한다. 원인이 구조적으로 제거됐다면 통제 축소·제거도 가능하지만 보호 공백이 없다는 근거와 권한이 필요하다. 비용만으로 필수 통제를 없애지 않는다.

위험에 비례하는 통제와 남은 위험이 확인되고 추가 통제가 의미 있는 보호를 제공하지 않으면 탐색을 종료한다. 아무 Gate도 추가하지 않는 선택도 타당할 수 있다.

## 경계와 반례

- 반복 API 계약 오류: 발생 원인을 확인한 뒤 구조적 제약과 계약 테스트를 비교한다.
- 일회성 문구 오타: 모든 변경에 승인 Gate를 추가하면 관리 비용이 이익보다 클 수 있다.
- 타입으로 표현을 제한해도 외부 데이터·런타임 경계의 위험은 남을 수 있다.
- 에이전트의 요구사항 준수는 문장 존재 여부가 아니라 실제 판단·행동 증거로 평가한다.
- 새 권한 경계가 기존 위험을 제거해도 종전 검사가 보호하던 다른 계약이 남아 있는지 확인한다.

**책임 경계:** Risk Management는 현재 선택의 위험·대응·잔여 위험을 판단한다. 이 원칙은 지속적 통제의 필요성과 수단·효과를 판단한다. 테스트 작성 품질, 구체 구현 방식, 실제 작업 절차를 다시 정의하지 않으며 SDD·Hide 개발 Workflow의 Gate를 변경하거나 호출하도록 강제하지 않는다.

**근거 수준:** 검토한 위험을 장기적으로 방지할 Gate의 필요성까지 평가해 달라는 사용자 발언에서 도출한 후보 원칙이다. 모든 위험의 자동 차단이나 특정 방법론을 사용자가 확정했다는 뜻은 아니다.
