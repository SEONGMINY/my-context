# Code Clarity — 의도를 드러내는 구현

**판단 원칙:** 코드는 중요한 역할·입출력·부작용을 주변 구현에 대한 추측 없이 이해할 수 있도록 작성한다. 명료함을 위한 변경도 새 추상화와 탐색 비용을 만들 수 있으므로, 이해와 변경 비용이 실제로 줄어드는지 검토한다.

## 적용 조건

구현·리팩터링·코드 리뷰 중 이름의 의미가 불분명하거나, 함수의 역할이 섞이거나, 숨은 의존성·상태 변경 때문에 동작을 추론하거나 테스트하기 어려울 때 적용한다. 이미 충분히 명확한 작은 코드에 형식적인 분리를 강제하지 않는다.

## 판단 기준

1. **이름과 맥락:** 식별자가 값의 역할·의미·단위를 구분하는가? 주변 구현을 다 읽어야 알 수 있는 약어·포괄적 이름에 의존하지 않는가? 관용적이고 범위가 좁은 이름은 허용할 수 있는가?
2. **함수의 책임:** 함수가 보장하는 결과를 한 가지 일관된 목적으로 설명할 수 있는가? 서로 다른 이유로 변경되는 판단과 작업을 함께 다루는가? 코드 길이만으로 분리하지 않는가?
3. **입력·출력:** 결과에 영향을 주는 필수 입력, 반환 결과, 오류 계약이 호출자에게 보이는가? 이름이나 타입만으로 오해할 여지는 없는가?
4. **의존성과 상태:** 외부 환경, 공유 상태, 시간, 난수, 저장소 등에 대한 의존성을 누가 소유하는가? 중요한 암시적 입력이 변경·검증을 어렵게 만드는가?
5. **부작용과 실패:** 상태 변경·I/O·로깅·자원 관리의 책임과 발생 위치를 추적할 수 있는가? 실패 경로를 성공 결과와 혼동하지 않는가?
6. **읽기 비용:** 단순화를 위해 분리한 함수·파일이 오히려 맥락 이동과 단순 전달 계층만 늘리지는 않는가? 기존 관례와 도구로 해결 가능한가?

## 구현 선택

| 판단 | 선택 기준 |
| --- | --- |
| **이름 개선** | 의미를 구분하기 어렵거나 잘못된 역할을 암시할 때 |
| **함수 분리** | 책임·변경 이유·독립 검증 필요성이 실제로 구분될 때 |
| **입출력 명시** | 숨은 상태·환경 의존성으로 결과를 예측하거나 검증하기 어려울 때 |
| **부작용의 경계 지정** | 호출자가 의도하지 않은 효과를 추적하기 어렵거나 수명주기 책임이 불분명할 때 |
| **유지** | 더 나누거나 추상화하면 오히려 이해·수정 비용이 늘어날 때 |

## 예외와 비적용

- 모든 변수명을 길게 쓰지 않는다. 의미가 자명한 짧은 식별자는 허용한다.
- 하나의 절차가 여러 단계를 갖는다는 이유만으로 단일 책임 위반이라고 판단하지 않는다.
- 모든 의존성을 모든 함수 호출의 인자로 반복 전달하지 않는다. 생성·조립 경계에서 명시되는 의존성도 적절하다.
- 순수 함수만을 강제하거나 모든 부작용을 제거하려 하지 않는다. 필요한 효과를 적절한 소유자가 관리하도록 한다.
- 스타일 규칙은 대상 언어·팀의 포매터·린터를 따른다. 특정 문법 규칙이나 도구를 범용 개발 철학으로 승격하지 않는다.

**다른 원칙과의 경계:** Responsibility-driven Design은 요소 간 정책·책임·협력 소유권을 판단한다. 이 자산은 해당 요소의 **구현 표현**이 명확한지를 판단한다. Implementation Strategy는 기술·패턴 선택, Testing Principles는 검증 가치와 테스트 설계를 다룬다. 한 자산의 사용이 다른 자산 호출을 강제하지 않는다.

**근거 수준:** 구현 시 이름, 함수 역할, 입출력, 의존성과 부작용을 명확히 하려는 반복 검토에서 추출한 후보 원칙이다. 모든 프로젝트에 같은 코드 스타일을 적용하라는 의미는 아니다.
