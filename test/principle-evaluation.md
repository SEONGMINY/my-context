# 개인 판단 원칙 행동 평가

이 문서는 `content/personal/`의 **Context-aware Reasoning(CR), Implementation Strategy(IS), Execution Strategy(ES), Roadmap Planning(RP), Risk Management(RM), Preventive Engineering(PE), Evidence-driven Improvement(EDI), Responsibility-driven Design(RDD), Code Clarity(CC)** 아홉 자산을 평가한다. SDD·Hide 기반 `development-workflow`의 G1~G6, Node/Step, Handoff 실행 절차를 변경하거나 대신하지 않는다.

## 1. 평가 목적과 기본 계약

- **의도 보존:** 사용자 확정 지시, 현재 프로젝트 계약, 실제 확인한 사실을 후보 개인 원칙보다 우선한다. 원칙은 과거 경험에서 *일반화한 후보*이며 사용자 확정 철학으로 승격하지 않는다.
- **읽기 허용:** 개인 자산 자동 조회는 기본적으로 비활성이다. 명시적 요청 또는 사용자가 활성화한 정책 범위에서만 조회한다. 테스트에 원칙 본문을 직접 제공하는 **통제 실험**과 운영 MCP의 실제 자동 검색을 구분한다.
- **작업 범위:** 요청이 검토·설계라면 평가 세션에서 코드·커밋·푸시·배포를 하지 않는다. 외부 도구가 없거나 실행 권한이 없으면 수행했다고 말하지 않는다.
- **테스트의 두 층:** Fixture의 형식·자산 존재 여부·CI 성공은 **정적 검사**다. 기대·금지 행동이 실제 응답·도구 호출·변경 파일에 드러났을 때만 **모델 행동 검사**를 통과 처리한다.

## 2. 기준선과 비교 대상

- 기준선: 변경 이전 리비전의 해당 `knowledge.md` 본문과 SHA를 기록한다. 새로 추가된 원칙은 해당 원칙 없이 동일 요청을 수행하는 비교군을 사용한다.
- 변경본: 평가 대상 리비전의 해당 원칙과 SHA를 기록한다.
- 공통 조건: 모델·에이전트 버전, 접근 가능한 도구·저장소 상태, 요청·프로젝트 계약, 실행 온도·컨텍스트 조건이 비교 가능해야 한다.
- 별도 독립 세션을 사용하고 한 시나리오의 메모리·파일 변경이 다른 결과에 영향을 주지 않게 한다.
- 기존 원칙에 있던 **적용 조건, 판단 기준, 예외, 후보 근거 수준**이 변경본에서도 유지되는지 먼저 확인한다.

일부 비교 요소를 고정할 수 없으면 그 제약을 기록한다. 모델이나 도구가 달라진 경우 문서 변경만으로 품질 차이가 생겼다고 단정하지 않는다.

| RDD | 책임 소유권·협력과 규칙 정의 위치의 구분 | 분리 대신 유지·통합을 선택할 수 있는지 | RDD-01~03 |

시나리오는 **완결된 현실의 모든 경우를 뜻하지 않는다**. 실제 실패가 새로 확인되면 해당 상황을 먼저 분석한 후 관련된 경계 사례를 추가한다. 새 시나리오를 작성한 모델에게 같은 시나리오만 반복해서 맞추게 할 경우 과적합 위험이 있으므로 독립적인 미사용 사례도 확인한다.

## 4. 실제 에이전트 평가 방법

1. 기준선 커밋과 변경본 커밋을 각각 고정한다. 비교할 원칙의 `knowledge.md`만 별도로 제공한다. 원칙 선택 능력을 평가할 때는 `SKILL.md` 진입 설명과 조회 권한도 함께 검증한다.
2. 각 Fixture의 `context`를 프로젝트의 확인 가능한 사실로 제공하고, `request`를 사용자 요청으로 제시한다. 실제 파일 작업이 필요한 사례는 격리된 테스트 프로젝트에서만 실행한다.
3. **실제로 한 행동**을 기록한다. 문서 속 문구를 복창했는지 대신, 무엇을 조회·질문·결정·변경·거절·보고했는지 본다.
4. `expected`의 중요한 행동을 충족했는지, `forbidden`을 위반했는지 **각각** 판정한다. 상황에 필요한 근거가 부족해 올바른 선택을 할 수 없으면 누락 사실을 기록하고 조건을 고쳐 재실행한다.
5. 단일 원칙 CR/IS/ES/RP/RM/PE/EDI/RDD/CC 사례와 교차 X 사례를 분리해 비교한다. 명시적으로 허용되지 않은 개인 지식 조회나 프로젝트 계약 위반은 중대한 실패로 기록한다.
6. 실패 원인을 `규칙 누락 / 규칙 간 충돌 / 표현 모호 / 평가 환경·도구 문제 / 모델 행동 오류 / 판정 근거 부족`으로 구분한다. 문서 누락·모호성인 경우에만 해당 원칙을 수정하고 관련 사례를 재평가한다.

새 원칙과 수정된 원칙의 사례는 그 원칙의 고유 판단을 검증해야 한다. EDI 사례에서 무조건 계측·자동화를 제안하거나 관측되지 않은 행동을 단정하지 않는지, IS 사례에서 이름 있는 패턴을 맹목적으로 선택하지 않는지 확인한다. 본문의 특정 기술 사례를 정답으로 암기시키지 않도록 평가 Fixture와 별도로 독립적인 미사용 상황도 점검한다.

### 자산 독립성 검증

- 각 단일 원칙 사례는 해당 본문만 제공하여 판단할 수 있는지 확인한다. 별도 Workflow나 다른 원칙의 호출을 전제로 하지 않는다.
- 실행 방식 검토에서 Node/Step 형식이나 인계 절차를 강제하지 않는지, 위험 검토에서 변경 권한을 확대하지 않는지, 예방 검토에서 Gate 추가를 자동 선택하지 않는지 관찰한다.
- 여러 원칙과 기존 Workflow를 함께 사용하는 비교군에서는 판단과 실행 계약이 충돌하거나 절차를 중복 수행하지 않는지 확인한다. 기존 Workflow 본문은 변경하지 않는다.
- 기존 asset-use 사례의 명시적 요청·선택적 조회·작은 변경 생략 조건을 유지한다.

각 사례의 판정은 `PASS / FAIL / NOT_RUN` 중 하나다. 일부 행동만 충족하면 `PASS`가 아니다. 정적 검사 성공과 운영 환경의 MCP 연결은 모델 행동의 PASS 증거가 아니다. 평가를 실행하지 못하면 원인과 미검증 범위를 명확하게 보고한다.

## 5. 수용·중단 조건

- 모든 변경된 규칙이 기존 원칙의 판단 목적 또는 명확한 사용자 요구·연구에서 유도된 *제안*과 연결돼 있는가?
- 기존 의도의 핵심이 약화·삭제되거나, 후보 원칙이 확정 철학처럼 표현된 경우는 수정한다.
- 중요 계약 위반, 임의 행동, 금지된 파일·권한 변경, 가짜 Sub-agent·검증 결과는 다른 지표가 개선돼도 전체 성공으로 취급하지 않는다.
- 모델 행동 평가를 실행할 수 없는 환경에서는 **문서 작성/정적 검증 완료**와 **행동 검증 미완료**를 분리한다. 행동 효율 개선·정확도 개선을 실측했다고 주장하지 않는다.
- 문서 압축·분리는 위 경계를 검증한 후에만 고려한다. 읽는 순간 필요한 주요 조건·우선순위가 누락되는 압축은 거부한다.

## 6. 범위 보호

- 개인 원칙 효과를 분리해 평가하는 비교군에서는 Workflow와 해당 Fixture를 고정한다. 이는 별도로 승인된 Workflow 유지보수를 금지하는 정책이 아니다.
- 본 문서는 개인 원칙 선택과 판단 품질을 평가할 뿐 SDD·Hide 절차나 실행 단계를 지시하지 않는다.
- 운영 배포는 별도 승인·검증 절차가 필요하다.
