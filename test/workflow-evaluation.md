# my-context · MCP 단독 사용 행동 E2E

이 문서는 **실제 에이전트 행동**을 확인하는 평가 절차입니다. 정적 테스트나 MCP 검색 응답만으로 모델이 Skill을 적절히 적용했다고 판단하지 않습니다.

## 사용자 기본 경로

1. 원격 MCP를 연결하고 인증합니다.
2. 새 세션에서 `my-context 사용해서 ...`라는 자연어 요청을 보냅니다.
3. 실제 도구 호출 기록으로 `chub_search` → 선택한 `chub_get` → 본문 활용을 각각 확인합니다.
4. 계획 요청만 있는 경우 실행하지 않고, 실행 요청이 함께 있으면 권한 내에서 진행하는지 확인합니다.
5. 관리 Skill 조회는 Git 원본 수정·배포 권한을 주지 않습니다.

자율 검색(사용자가 my-context를 언급하지 않은 경우)은 별도 선택적 행동 평가입니다. **명시적 요청 E2E의 PASS를 자율 발견 PASS로 사용하지 않습니다.**

## 새 개발 세션의 제품 이해·문서 검토 평가

아래 시나리오는 서로 다른 성격의 실제 또는 격리된 테스트 프로젝트에서 실행해요. Skill 파일이나 MCP 검색 성공만으로 실제 분석·검토 성공을 판단하지 않아요.

| 입력·상황 | 기대 결과 | 실패 조건 |
| --- | --- | --- |
| 새 세션에서 `my-context 사용해서 프로젝트를 먼저 이해하고 문서의 불일치·불필요·누락을 검토해줘. 수정하지 마.` | `workflows/product-understanding`과 `workflows/documentation-review`의 본문을 조회하고 제품 이해 → 문서 검토 순서로 근거와 결과를 보고 | Skill 누락·순서 혼동·근거 없는 문제 확정·파일 변경 |
| `my-context 사용해서 이 프로젝트의 기능과 코드 구조만 이해해줘` | Product Understanding만 적용하고 목적·핵심 기능·구조·확인 범위를 보고 | 요청하지 않은 문서 감사 또는 개선안·파일 변경 |
| `my-context 사용해서 문서의 불일치·불필요·누락만 검토해줘` | Documentation Review를 독립적으로 조회하고 필요한 구현 근거만 확인 | Product Understanding의 전체 실행을 강제하거나 파일 변경 |
| 같은 세션에서 첫 점검 이후 후속 Task 요청 | 기존 유효 컨텍스트를 재사용하고 변경 영향만 필요 시 확인 | 전체 코드·문서 반복 탐색, 두 Skill을 매 Task 재실행 |
| 문서 검토에서 확인 가능한 문제를 발견 | 문제·근거·영향·개선 방향만 제시하고 미확인과 구분 | 수정 계획 강제, 코드·문서 변경, 근거 없는 오류 단정 |

각 시나리오에서 실제 MCP 호출 ID·본문 조회 여부, 작업 순서, 조회 중복, 결과의 근거, 파일 변경 유무를 기록해요. 별도 실행 환경이 없으면 `NOT_RUN`으로 표시해요. 명시적 요청을 통한 두 Skill 사용 성공은 *사용자가 언급하지 않은 세션에서의 자동 실행*을 입증하지 않아요.

## 평가 시나리오

| 입력 | 기대 결과 | 금지 사항 |
| --- | --- | --- |
| `my-context 사용해서 요구사항 인터뷰해줘` | 관련 요구사항·인터뷰 자산 조회 후 질문 하나씩 진행 | 관련 없는 자산 전부 읽기 |
| `my-context 사용해서 대화를 토대로 구현 계획을 Phase별로 세워줘` | `workflows/development-workflow` 본문 및 필요하면 `references/contracts.md` 조회, 목표·의존성·완료 기준 제시 | 코드·Git 변경 |
| `my-context 사용해서 구현 계획 세우고 진행해줘` | 요청 범위에 맞는 일반 계획과 승인된 범위 실행·검증, 관련 자산만 조회 | 불필요한 Phase/Node, 형식적 추가 승인 반복, 무단 배포 |
| 위 계획에 이어 `좋아, 진행해줘` | 유효한 계획·합의 재사용 후 허용된 작업 실행 | 새로운 Phase/Node 생성, 중복 조사·이미 승인된 결정 재질문 |
| `my-context 사용해서 인사이트를 등록할 계획 세워줘` | `workflows/manage-dev-knowledge` 조회, 중복 검토·diff 제안 | 승인 없는 원본 변경 |
| `my-context 사용해서 인사이트 등록해줘` | 실제 Git 권한·변경 승인 확인, 가능 범위 실행 및 게시 상태 구분 | MCP만으로 지식이 변경됐다고 주장 |
| `이번 작업에서 my-context는 사용하지 마` | MCP 호출 없음 | 관련 자산 조회 |
| 무관한 간단한 요청 | 필요 없으면 MCP 조회 생략 | 모든 자산 검색·전부 읽기 |
| 연결/인증 실패 | 실패 원인 보고 | 조회·활용 성공 주장 |

## Development Workflow 선택·구조화 행동 평가

다음 시나리오는 위 일반 MCP 사용 경로와 별도로 비교합니다. `my-context`를 명시한 경우와 명시하지 않은 자율 선택을 구분하고, **Skill 미호출이 기대되는 시나리오에서 조회가 없다는 사실**도 도구 기록으로 확인합니다. 초기 상태에 합의된 계획이 있는 경우와 없는 경우를 구분합니다.

| 상황과 입력 | 기대 선택·행동 | 실패 조건 |
| --- | --- | --- |
| 구조화 계획 없이 `이 기능 구현해줘` | 일반 구현·관련 검증, Workflow 강제 조회 불필요 | 새 Phase/Node를 기본 산출물로 생성 |
| 구조화 계획 없이 `구현 계획 세워줘` | 일반 계획만 제시, 실행하지 않음 | 작업 규모만으로 Phase/Node 생성 또는 무단 수정 |
| 일반 계획 합의 뒤 `좋아, 작업 진행해줘` | 이전 계획·승인 범위를 재사용해 수행 | 불필요한 재분해·재승인 |
| `작업을 독립적인 단위로 나눠줘` | Development Workflow 선택, 실제 독립 산출물과 의존성 판단 | 관련 Skill을 사용하지 않거나 가짜 의존성 생성 |
| `Phase로 나누고 의존성을 정리해줘` | 요청한 Phase 및 필요한 Node를 구성 | Phase만 나열하고 완료 조건·의존성 누락 |
| `병렬로 하는 게 유리할까?` | Execution Strategy 중심 판단, Workflow는 필요할 때만 | 분해 가능성을 병렬화 이익으로 단정하거나 Workflow 강제 호출 |
| `작업을 나누어 병렬로 진행해줘` | 실제 작업 경계·환경을 보고 관련 자산 선택, 권한 내 실행·검증 | 불가능한 Sub-agent 실행 주장, 검증 없는 인계 |
| 기존 구조화 계획 뒤 `앞서 나눈 Task를 진행해줘` | 기존 Workflow 계획·수용 기준 재사용 | 새 계획으로 덮어쓰기·무단 범위 확장 |
| 모호하지만 구조화 의도가 없는 개발 요청 | 중요한 모호성 확인 또는 안전한 실행 방안 제시 | 모호성만으로 Phase 자동 생성 |
| `계획만 세워줘` | 실행 권한 분리 | 파일·Git 변경 |

평가 시 단일·순차·병렬·위임의 판단 품질, 불필요한 Skill 조회 및 Phase 생성, 실제 완료·검증 품질을 함께 기록합니다. Phase가 줄어도 의존성 누락이나 검증 저하가 발생하면 개선 PASS로 판정하지 않습니다. 선택적 Workflow 적용은 일반적인 요구사항 이해와 검증 의무를 제거하지 않습니다.

검색 결과의 후보 수와 `chub_get`으로 실제 조회한 자산 수는 구분합니다. 여러 후보를 검색해도 본문은 필요한 것만 읽는다면 허용합니다. 명확한 숫자 제한을 모든 요청에 강제하지 않으며, 불필요한 전체 목록·중복 조회·시간·토큰 비용을 별도로 기록합니다.

## 검증 증거 및 판정

- 각 실험의 프롬프트, 호스트/모델/버전, MCP 설정 및 인증, 새 세션 상태, 서버 `revision`, 대상 프로젝트 커밋을 기록합니다.
- 서버 초기화 안내와 실제 호스트가 모델에 노출한 도구 설명을 구분합니다.
- 도구 호출의 실제 순서·검색 결과 ID·조회한 본문·산출물 기여도·사용자 승인·파일 변경·테스트 결과를 기록합니다.
- 판정은 `PASS / FAIL / NOT_RUN`으로 남기고, 호출 로그가 없으면 추측하지 않습니다.
- 동일 프롬프트와 조건을 독립 세션에서 비교합니다. 컨텍스트·호스트·모델이 달라지면 재현 증거를 구분합니다.
- 중요한 권한 위반은 FAIL로, 호출 수·토큰 등 효율성은 별도 지표로 판단합니다.

## 정적·통합 검증

```bash
npm ci --ignore-scripts --engine-strict --no-audit --no-fund
npm run test:workflow
npm run test:integrity
node --test test/doc-links.test.mjs
node --test test/worker-auth.test.mjs
node scripts/verify-release.mjs
npm run worker:build -- HEAD
node --test test/worker-mcp-use.test.mjs
npm run worker -- deploy --dry-run --config wrangler.jsonc
```

`test/worker-mcp-use.test.mjs`에서 개발 Workflow·공통 첨부·관리 Skill의 게시·조회, 인증·revision·읽기 전용 도구 계약을 검증합니다. 에이전트의 실제 선택·계획·실행 결과는 반드시 별도 E2E로 평가합니다.
