# 개발 경험에서 판단 원칙 추출

사용자가 지정한 개발 대화·작업 경험에서 **재사용 가능한 판단 기준의 후보**를 찾는다. 목표는 모든 대화를 요약하거나 새 Skill을 만드는 것이 아니다. 사용자의 실제 질문과 선택이 어떻게 구현·검증으로 이어졌는지 복원하고, 다른 상황에도 적용 가능한지 검토한다.

## 적용 범위와 권한

- 사용자가 자신의 대화·경험에서 인사이트 도출을 **명시적으로 요청한 경우에만** 적용한다. 다른 개발 작업 중 과거 대화나 개인 지식을 자율적으로 검색하지 않는다.
- 대상 기간·프로젝트·자료를 확인한다. 현재 제공된 원문과 접근 가능한 원본을 사용한다. 직접 열지 못한 대화·코드·로그를 읽었다고 주장하지 않는다.
- 분석은 **읽기 전용**이다. Skill 실행 자체는 지식 등록, 파일 생성·수정, 커밋·푸시, 운영 배포를 승인하지 않는다.
- 사용자의 최신 지시와 해당 프로젝트 계약을 우선한다. 사적인 대화 원문·인증정보·개인 식별 정보는 공개 자산에 옮기지 않는다.

## 1. 실제 흐름 복원

1. 사용자가 **어떤 문제를 제기하고 무엇을 요구했는지** 시간순으로 파악한다. 사용자의 원문 발언, AI의 제안, 사용자의 승인·정정, 실제 구현과 검증 결과를 각각 구분한다.
2. 중요한 결정은 당시 검토한 대안, 선택·보류·제외한 이유, 제약, 후속 변경을 연결한다. 실제로 논의되지 않은 대안을 **당시 선택지**로 만들지 않는다. 나중에 찾은 대안은 **현재의 추가 분석**으로 표시한다.
3. 범위·중장기 계획·작업 분해·실행 방식·인계 등의 논의를 포함하되, 대상 자료가 뒷받침하는 내용만 확정적으로 설명한다.
4. 인용·근거의 출처를 연결한다. 원문을 확인할 수 없다면 해당 내용은 미확인으로 남기고, 부분 기록을 전체 대화인 것처럼 표현하지 않는다.

## 2. 인사이트 후보 도출

- 사건 자체가 아니라 **어떤 조건에서 무엇을 고려해 판단했는가**를 추출한다. 예를 들어 “병렬 실행을 요청했다”를 “병렬화하라”로 변환하지 않는다.
- 후보마다 적용할 상황, 결정에 영향을 주는 요소, 선택·제외 기준, 예외·반례, 확인되지 않은 가정을 살핀다.
- 철학(여러 결정의 가치 기준), 원칙(조건부 판단 기준), 절차(반복 가능한 적용 단계)를 구분한다. 구분 자체가 산출물 생성을 강제하지는 않는다.
- 하나의 경험으로 효과가 입증됐다고 일반화하지 않는다. 관찰 사실, 사후 해석, 아직 검증할 가설을 구분한다. 사용자에게서 직접 승인받지 않은 표현을 **사용자가 확정한 철학**으로 소개하지 않는다.
- 새로 추출할 내용이 없거나 기존 원칙으로 충분하면 **새 후보 없음**도 유효한 결과다.

## 3. 기존 자산과 대조

사용자가 기존 지식과의 비교를 요청한 범위에서만 접근 가능한 원본을 조회한다. 이미 제공된 자산을 먼저 사용하고 불필요한 반복 조회를 하지 않는다.

- 기존 원칙·Skill에 이미 포함됐는가?
- 별도 지식이 필요한가, 기존 자산의 사례·조건만 보완하면 되는가?
- 다른 프로젝트에서 재사용할 가치가 있는가? 새 자산을 유지할 비용보다 효과가 큰가?

**기존 내용 / 보완 후보 / 독립 후보 / 아직 근거 부족**으로 구분한다. 특정 저장소나 MCP 연결이 없어도 분석 가능한 범위부터 수행한다.

## 결과와 인계

작업 규모에 맞춰 짧게 보고한다. 복잡한 대화에서는 아래 내용을 식별할 수 있게 제시한다.

- 사용자 발언·문제 → 검토된 대안·당시 선택 → 실제 결과 (근거와 확인 상태)
- 도출한 철학·원칙·절차 **후보** → 적용 조건·예외 → 기존 자산과의 관계
- 확인할 수 없는 원문, 반례, 사용자 결정이 필요한 항목

**분석과 저장은 별개다.** 사용자가 실제 등록·수정을 명시적으로 요청했을 때만 기존 `manage-dev-knowledge`의 원본 확인·중복 검토·diff·승인 절차로 인계한다. 이 Skill이 자동으로 등록하거나 그 Skill을 우회하지 않는다.
