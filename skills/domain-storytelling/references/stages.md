# 도메인 스토리텔링 단계별 진행 지침

요청한 단계의 입력을 확인한다. 기존 자료로 충분하면 그 근거를 참조하고, 현재 결정을 막는 공백만 확인한다. 단계별 산출물은 프로젝트의 기존 문서에 함께 둘 수 있다.

## AS-IS

- **입력** — 대상 업무, 프로젝트 목적과 제약, 원문과 기존 해석, 참여자가 알고 있는 범위.
- **인터뷰** — 업무 목적과 참여자부터 확인한다. 한 번의 대표 업무가 어떤 계기로 시작하고, 누가 무엇을 보고 판단하며, 어떤 순서로 행동하는지 묻는다. 판단에 쓰는 정보의 출처와 직접 행동하는 참여자를 확인한다. 다음 행동, 일의 종료, 미완료 업무의 재개를 이해하는 데 필요한 분기를 따라간다. 새 정보가 나오지 않으면 전체 흐름으로 돌아간다.
- **산출물** — 목적·범위와 AS-IS의 기준, 시작·종료 조건, Actor·Activity·Work Object·Sequence가 드러나는 이야기, 주요 분기, 합의한 업무 규칙, 근거와 미확인 사항. 시각화가 합의됐다면 참여자·활동·업무 대상의 관계와 순서를 보여준다.
- **완료** — 사용자가 전체 흐름에 동의한 뒤 구성 요소와 업무 경계를 확인했다. 작성한 문서를 인터뷰와 대조해 판단 이유와 후속 행동을 점검했다.

## Pain Point·Scope

- **입력** — AS-IS 업무 흐름, 프로젝트 목표, 원문상 필수 조건과 제약.
- **인터뷰** — 어느 업무 단계에서 어려움이 생기는지, 얼마나 반복되는지, 어떤 영향이 있는지 묻는다. 문제, 원인 가설, 영향, 해결책 제안을 구분한다. AS-IS에서 깊게 탐색한 분기도 같은 기준으로 다시 평가한다. 범위를 바꿀 가능성이 있는 질문은 원문과 현재 목적을 확인한 뒤 다룬다.
- **산출물** — 업무 단계에 연결된 문제와 근거, 핵심·부차 문제, 이번에 해결할 범위와 제외 이유, 문제에서 직접 나오지 않았더라도 충족해야 하는 원문상 필수 조건.
- **완료** — 문제의 우선순위와 포함·제외 범위를 사용자가 확인했다. 사용자 조사로 검증되지 않은 문제는 가설로 표시했다.

## TO-BE

- **입력** — AS-IS, 해결하기로 한 문제와 범위, 필수 조건.
- **인터뷰** — 대상 업무 단계에서 무엇이 달라져야 하는지 묻는다. 누가 정보를 만들고 누가 판단하고 행동하는지, 사람과 시스템의 책임이 어떻게 바뀌는지 확인한다. 필요한 시스템 지원을 업무 흐름의 변화로 설명한다.
- **산출물** — 해결할 문제와 연결된 미래 업무 이야기, 참여자·활동·업무 대상·순서, 역할과 규칙의 변화, 남은 질문. 합의한 경우 흐름도를 포함한다.
- **완료** — 사용자가 바뀐 흐름과 책임에 동의했고, 각 변화가 이번 범위의 문제나 필수 조건에 연결된다.

## User Stories

- **입력** — TO-BE의 활동과 판단, Pain Point·Scope, 앞 단계에서 합의한 업무 규칙.
- **인터뷰** — 각 활동에서 사용자가 달성하려는 목표와 이유를 확인한다. 목표가 같으면 함께 묶을 수 있다. 분기가 별도의 목표나 완료 조건을 만들면 구체적인 업무 상황을 놓고 판단한다. 구현 예외의 결정이 지금의 사용자 목표나 완료 조건에 필요한지 확인한다.
- **산출물** — 사용자·목표·이유, 완료 조건, TO-BE나 문제·필수 조건으로 이어지는 참조, 이후 단계에서 정할 항목.
- **완료** — 사용자가 목표와 완료 조건을 확인했다. 별도로 남긴 목표에는 업무상의 이유가 있다.

## Requirements

- **입력** — User Stories와 완료 조건, 원문상 필수 요구사항과 구현 제약, 합의한 업무 규칙.
- **인터뷰** — 시스템이 어떤 조건에서 어떤 동작과 결과를 제공해야 하는지 정한다. 구현 시 결과를 가르는 판단 시점, 상태 전환과 종료 경계를 필요한 만큼 구체화한다. 원문과 교차 확인해 필수 조건을 빠뜨리지 않았는지 검토한다. 결정이 추가 업무를 만드는 경우 현재 범위에서 필요한지 확인한다.
- **산출물** — 검증 가능한 필수 동작과 조건, 관련 User Story 또는 원문 참조, 구현 제약, 검증 시나리오, 제외 범위와 미결정 정책.
- **완료** — 구현자가 기대 결과를 확인할 수 있고, 원문상 필수 조건을 추적할 수 있다. 결정에 필요한 근거가 부족한 정책은 미결정으로 남겼다.

## UX Principles

- **입력** — 합의한 업무 흐름, 사용자 목표, 요구사항, 사용 환경과 프로젝트 제약.
- **인터뷰** — 사용자가 무엇을 읽고 판단하고 조작해야 하는지 중심으로 기준을 정한다. 대안을 설명할 때는 동일한 업무 조건에서 어떤 행동과 결과가 달라지는지 비교한다. 참고 서비스가 필요한 경우 관찰한 동작과 이 프로젝트에 적용할 수 있는 근거를 기록한다. 새 기능은 요구사항과 업무 목표에 기여하는지 확인한다.
- **산출물** — UX 원칙과 선택 근거, 연결된 요구사항, 검증할 설계 가설, 검증 기준, 제외하거나 보류한 대안.
- **완료** — 사용자 행동을 기준으로 원칙을 검증할 수 있고, 원칙과 잠정적인 UI 선택의 상태가 드러난다.
