# 프로덕트 문서 검토

현재 프로젝트의 문서가 실제 프로덕트와 맞고, 해당 문서의 목적에 필요한 내용을 담고 있는지 검토한다. 프로젝트 종류·기술 스택·문서 이름에 종속되지 않는다.

## 시작

- 검토 대상 문서와 문서별 독자·목적을 확인한다. 현재 세션에서 확보한 제품 목적·기능·구조 이해를 먼저 재사용한다.
- 제품 컨텍스트가 부족하다면 문서 판단에 필요한 코드·설정·계약·테스트만 추가로 파악한다. product-understanding의 사전 실행이나 전체 저장소 재분석을 강제하지 않는다.
- 현재 구현, 문서에 적힌 주장, 과거 결정, 확인되지 않은 추측을 구분한다. 문서의 주장만으로 실제 동작을 확정하지 않는다.

## 세 가지 검토 기준

1. **불일치:** 문서의 기능·인터페이스·설정·실행 흐름·운영 설명이 현재 코드 또는 유효한 계약과 다른가? 어느 쪽이 의도된 계약인지 불분명하면 오류로 단정하지 않는다.
2. **불필요:** 더 이상 유효하지 않은 안내, 근거 없는 주장, 독자에게 불필요한 구현 세부사항, 실질적으로 중복된 설명이 있는가? 역사적 의사결정 기록이나 서로 다른 독자에게 필요한 설명을 단순 중복으로 삭제 대상으로 분류하지 않는다.
3. **누락:** 문서의 목적과 독자가 실제로 작업하거나 이해하는 데 필요한 중요한 설명이 빠져 있는가? 구현에 존재하는 모든 세부 사항을 문서화하도록 강제하지 않는다.

## 확인 및 결과

- 발견 항목마다 **유형 / 문제 / 문서와 구현의 근거 / 영향 / 개선 방향**을 간단히 제시한다. 대상 문서의 위치와 비교한 코드·설정·계약의 위치를 가능하면 식별한다.
- 직접 대조하지 못한 항목은 미확인으로 구분하고, 검토한 범위를 밝힌다. 확인한 범위에 문제가 없으면 발견된 문제 없음으로 보고한다.
- 개선 방향은 설명의 수정·제거·통합·보완 등 판단 수준에서 제시하며, 상세 수정 계획을 자동으로 작성하지 않는다.
- 필요한 확인이 끝나고 추가 탐색이 판단을 바꿀 가능성이 낮으면 종료한다. 기존 제품 컨텍스트와 유효한 근거는 중복 조회하지 않는다.

## 권한과 경계

읽기 전용으로 수행한다. 문서·코드 수정, 파일 생성, 커밋·푸시·배포는 하지 않는다. 수정이나 별도 구현 계획은 사용자가 이후 명시적으로 요청한 작업에서 다룬다. 세션 시작 시 product-understanding과 연속 사용할 수 있지만 독립 사용도 가능하며, 다른 Skill이나 세션 오케스트레이터의 자동 실행을 요구하지 않는다.
