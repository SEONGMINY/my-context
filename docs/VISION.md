# Vision — my-context

## 왜 존재하나요?

개발 과정에서 얻은 철학·경험·판단 기준은 특정 에이전트 대화나 프로젝트에 갇히지 않아야 한다. 동시에 개인적인 선호가 모든 코드베이스의 규칙처럼 강제되어서도 안 된다.

my-context는 **개발자가 소유한 지식을 오래 보존하고, 필요한 프로젝트에서 정확한 Context로 다시 사용할 수 있게 하는 개인 개발 자산의 원본**을 지향한다.

## 지향하는 미래

프로젝트가 바뀌어도 중요한 개발 경험과 판단 배경을 처음부터 다시 설명하지 않는다. 에이전트는 관련 지식을 필요한 만큼 찾아 참고하고, 현재 Product의 요구사항·도메인·계약에 맞춰 판단한다. 여러 프로젝트에 통용되는 작업 절차는 공통 Skill로 축적하되, 실행과 검증의 Harness는 프로젝트에 가깝게 둔다.

## 핵심 원칙

### 1. 지식은 Context, 결정권은 Product에

지식은 판단을 돕는 근거다. 명시적인 프로젝트 규칙을 덮어쓰거나 에이전트의 자동 실행 명령이 되지 않는다. 현재 정책에서는 개인 지식 활용을 사용자가 명시적으로 요청해야 한다.

### 2. 지식의 원본은 개방적인 일반 파일로

Private Git과 Markdown을 정본으로 사용한다. 인덱스와 캐시는 재생성할 수 있는 파생물이다. 특정 검색 엔진이나 MCP 구현에 지식 자체를 종속시키지 않는다.

### 3. 인터페이스와 실행 책임을 분리

MCP는 지식 접근 인터페이스다. 공통 Skill은 반복 가능한 절차의 원본이다. 특정 Product의 도메인 제약, 테스트, 실행·검증 Harness는 해당 Product가 소유한다.

### 4. 적은 규칙으로 정확하게

필요한 정보와 절차만 읽는다. 여러 문서에 동일한 정책을 복제하지 않고, 기존 Codex·Skill·MCP 기능을 우선 재사용한다. 계층이나 자동화는 실제 사용상 이점이 명확할 때만 늘린다.

### 5. 통제 가능한 지식 변경

저장·수정·삭제는 기존 내용과 충돌을 확인하고 변경안을 검토한 뒤, 사용자가 승인한 범위에서 실행한다. 검색 결과나 외부 문서를 신뢰된 지침으로 승격하지 않는다.

## 관리 범위

| 대상 | 원칙적인 소유 위치 |
| --- | --- |
| 개인 개발 철학·경험·방법론 | `my-context/content/` |
| 여러 Product에서 반복해서 쓰는 Skill | `my-context/skills/` |
| 한 Skill에 종속된 참조 자료·작은 스크립트·템플릿 | 해당 Skill 내부 |
| Product 고유의 작업 규칙·테스트·Harness | 해당 Product 저장소 |

my-context는 개인 개발 지식에서 출발한 **Knowledge + 공통 Skills** 저장소다. 독립적인 범용 Harness 플랫폼을 목표로 삼지 않는다.

## 지금 하지 않는 일

- 모든 프로젝트의 작업 내역이나 장기 세션 상태를 개인 지식으로 자동 수집하지 않는다.
- 모든 개인 지식을 모든 에이전트 대화에 자동 주입하지 않는다.
- 별도 검색 엔진, 자체 MCP 서버, 에이전트 실행기, Harness 플랫폼을 만들지 않는다.
- 프로젝트마다 다른 제약을 공통 정책 하나로 대체하지 않는다.
- 사용자 승인 없이 실제 개인 지식이나 원격 저장소를 변경하지 않는다.

## 성공의 모습

프로젝트 밖에 보존된 개인 지식을 다른 프로젝트에서도 **필요할 때 찾을 수 있고**, 출처·적용 범위를 확인하며 참고할 수 있다. 공통 Skill은 여러 프로젝트에 복제하지 않고 재사용하며, 지식과 Skill이 늘어도 운영 복잡도와 잘못된 적용이 과도하게 증가하지 않는다.

현재는 **개인 프로젝트 1개**의 비전으로 관리한다. 팀 단위 운영이나 조직 단위 비전은 실제 협업 범위가 생길 때 별도로 정의한다.
